## Details and reproductions

All shell snippets assume `export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` and a fixed
`GIT_AUTHOR_*`/`GIT_COMMITTER_*`; `cw` = `python -m crosswire` at `HEAD`. Helper `c "msg"` = `git add -A; git commit -qm`.

### V3-01 blocker — unchanged generated file crashes `--combined` and `plan` (exit 1, traceback)

`analyze_combined` re-checks target references by calling `_Analysis.references` on **every** `.py` file of the
integrated state (`combined.py:228-232`). `extract_references` uses a recursive `ast.NodeVisitor`
(`python_analyzer.py:248-283`); `_reference_data` only converts `SyntaxError` (`:290-292`), `engine.py:63`
and `state.py:50` likewise, and `cli.py:78` only catches `GitError`. Any `RecursionError` therefore escapes as a
Python traceback with exit code **1**, which the contract defines as "error findings present" (PLAN §1: crashes
must be exit 2 / never abort on unparsable sources, QUALITY §5: unparsable → `unknown` + warning).
A 500-term arithmetic/concatenation chain is enough (recursion limit 1000).

```
git init -q -b main r && cd r
python3 -c "print('x = ' + '+'.join(['1']*600))" > generated.py
printf 'def f():\n    return 1\n' > m.py; c base
git branch a; git branch b
git checkout -q a; printf 'def f():\n    return 2\n' > m.py; c a
git checkout -q b; printf 'y = 1\n' > n.py; c b
cw check a b                              -> "No semantic conflicts found across 1 pair(s)."  exit 0
cw check --target main --combined a b     -> RecursionError: maximum recursion depth exceeded  exit 1
cw plan  --target main a b                -> RecursionError: maximum recursion depth exceeded  exit 1
```

Threshold measured on a *changed* file in pairwise mode: 300 terms OK, 500 terms → traceback, exit 1.
The file is not touched by either branch, so pairwise is fine and only the new whole-repo scan trips on it.

Fix: (1) catch `(SyntaxError, RecursionError, ValueError, MemoryError)` at the single parse choke points
(`_reference_data`, `_build_module_data`, `analysis.parse`) and treat them like a parse failure (`unknown` +
one stderr warning); (2) make `main()` map any unexpected exception to exit 2 (`crosswire: error: internal error: …`)
so exit 1 always means "error findings"; (3) fix V3-05 so unchanged files are not parsed at all.

### V3-02 blocker — star import replacing a definition is reported as a removal

`from X import *` binds nothing in `extract_symbols` (`_import_names` skips `*`, `python_analyzer.py:80,83`), so
a module that moves its body behind a star import "loses" every name: `api_changes` emits `removed`
(`diffing.py:9-21`), `StateIndex._resolve` returns `broken` (`state.py:129-130`). `languages/python.md` lists
star-imports as "explicitly unsupported (reported as coverage gaps, never as conflicts)" and VISION V6 says
`unknown` is never reported.

```
mkdir app; touch app/__init__.py
printf 'def f(x):\n    return x\n' > app/m.py; cp app/m.py app/impl.py; c base
git branch refactor; git branch user
git checkout -q refactor; printf 'from app.impl import *\n' > app/m.py; c "m re-exports via star"
git checkout -q user; printf 'from app.m import f\n\nprint(f(1))\n' > app/use.py; c use
cw check refactor user                               -> CW001 [user × refactor] `app.m.f` is used here but was removed in refactor  exit 1
cw check --target main --combined refactor user      -> CW001 ... exit 1
cw plan --target main refactor user                  -> 1. refactor; Blocked: user: CW001 ...  exit 1
```

`app.m.f` is still importable. Fix: while building module data, record `has_star` (any module-level
`from … import *`, including guarded ones) and `has_dynamic` (V3-03). `resolve` returns `unknown` for a missing name in such a module;
`api_changes`/`ApiChange(removed)` is suppressed (or downgraded to a coverage note) when the *new* version of the
module has a star import or dynamic exports, in `rules/cw001.py` as well as `state.py`.

### V3-03 major — module `__getattr__` (lazy exports)

Same mechanism, dynamic variant: `def __getattr__(name): return getattr(importlib.import_module("app.impl"), name)`
in `app/m.py` (replacing `def f`) → CW001 in pairwise, combined and plan (reproduced exactly as V3-02 with that
body). Also affected (not run): `globals().update(...)`, `setattr(sys.modules[__name__], …)`, `__all__` built dynamically.
Fix: flag modules defining module-level `__getattr__` (and `globals()`/`sys.modules[__name__]` mutation) as
`unknown` for any missing name.

### V3-04 major — breakage caused by the target is blamed on the wrong branch (or on `{}`)

A branch's tip is `base + branch`; if the **target** advanced after the branch point and itself removed the
name, the branch's own reference is valid at its tip and broken in `I`. The culprit search only considers other
integrated branches that touched the consulted files and enumerates subsets of size ≥ 1 (`combined.py:197-208`,
`_subsets` starts at 1), so the target is never a candidate.

```
mkdir app; touch app/__init__.py
printf 'def f(x):\n    return x\n\ndef g():\n    return 1\n' > app/m.py; c base
git branch feat-use; git branch other
git checkout -q feat-use; printf 'from app.m import f\n\nprint(f(1))\n' > app/use.py; c use
git checkout -q other;    printf 'def g():\n    return 2\n' >> app/m.py; c "other touches m (innocent)"
git checkout -q main;     printf 'def g():\n    return 1\n' > app/m.py; c "main drops f"
cw check --target main --combined feat-use other
  -> CW001 [feat-use × {other}] `app.m.f` is used here but was removed in other   (culprits_exact: true)   WRONG BRANCH
git checkout -q -b dummy main; echo x > z.txt; c z
cw check --target main --combined --format json feat-use dummy
  -> CW006 ... "broken after merging {}: undefined; no single branch causes it", culprits [], culprits_exact false,
     "coverage": "bounded", "limits.hit": ["max_group"]
```

The break itself is real (target vs branch), but the report blames `other`, an exact-looking culprit that
cannot be right (trial `T+feat-use+other` reproduces only because `T` is in every trial), or prints an empty
set. In a plan, `other` would be wrongly advised ("merge a compatible fix first"). The same flaw sits in the
target-reference path (`:258-271`) and in `resolved_by`.
Fix: always test the size-0 subset first (`T + owner` alone); if it already breaks, culprits = `{<target label>}`,
`culprits_exact: true`, rule CW001/CW002 with message "…was removed in <target>". Requires the architect to
decide the wire form (target label in `culprits`).

### V3-05 major — whole-repo scan per state; `plan` is impractical on medium repos

`combined.py:228-232` iterates `git.list_files(I)`, reads each `.py` blob at `T` and at `I` and extracts references
(`engine.py:76-89`), although T10 (PLAN-v0.3b) restricts this to files that import a module that differs between
`T` and `I`. The blob read at `I` is a new `cat-file` round trip for every file in every state (new commit sha ⇒
`_read_file_sha` miss). `plan` calls `analyze_combined` per state (`planner.py:75`), which also re-runs
`repo_root`, `git --version`, `rev-parse` for all labels, and summary-cache loads each time; `planner.py:64-67`
spawns `n(n-1)` `git merge-base --is-ancestor` processes.

Measured (synthetic repo, 9 051 files, 16 independent branches each touching 2 files, all independent, no conflicts,
warm cache, shared dev machine):

| mode | time |
| --- | --- |
| `check --target main` (pairwise, 120 pairs) | 1.7 s |
| `check --target main --combined` | 5.8 s (cProfile: 18 102 `references()` calls = 2 × files, 4.9 s of 9.0 s) |
| `plan --target main` | **95.1 s** (16 states × ~6 s) |

3 051 files / 8 branches: pairwise 0.6 s, combined 1.9 s (warm cache gives no gain), plan 6.9 s. In a tiny repo
`plan` of 16 trivial branches spawns 562 git processes (256 `merge-base`, 205 `rev-parse`) vs 71 for `--combined`.
With blocked branches the greedy loop evaluates O(n²) states (each remaining label per step), so (extrapolating, not measured) a 30-branch
plan on a large repo is minutes or worse — the v1.0 performance matrix (30 branches × 50k files) is out of reach.
Also (`combined.py:283-345`): the "resolved_by"/CW003/CW004 loops run over **all** O(n²) live pairs without the engine prefilter.

Fix: build the target-reference candidate set once per `T` (reverse index `module → files importing it`, from
`git grep`/one pass at `T`) and, per state, look only at files whose imports hit `changed_paths`; memoise per
state in `plan`; resolve refs/`repo_root`/version once per `plan`; replace the pairwise ancestor probes by one
`git rev-list --parents`/`merge-base --independent` pass; apply the prefilter to the pair loops.

### V3-06 major — combined mode misses a break that pairwise reports (and claims `complete`)

In `pkg/__init__.py`, `from . import util` is recorded by `_build_module_data` as the binding
`util → ('pkg', 'util')` — i.e. the module itself (`state.py:64-73`: `target = 'pkg'`, name `util`).
`_resolve('pkg','util')` then recurses into `('pkg','util')`, hits `key in seen` and returns `unknown`
(`state.py:119`), so `from pkg import util` at the tip is never `valid` and is skipped (`combined.py:185`).
The submodule file `pkg/util.py` is never consulted.

```
mkdir app; printf 'from . import util\n' > app/__init__.py; printf 'def h():\n    return 1\n' > app/util.py
printf 'x = 1\n' > app/z.py; c base
git branch rmutil; git branch user
git checkout -q rmutil; git rm -q app/util.py; printf '' > app/__init__.py; c "remove util"
git checkout -q user; printf 'from app import util\n\nutil.h()\n' > app/use.py; c use
cw check rmutil user                               -> CW001 `app.util` removed in rmutil   exit 1
cw check --target main --combined rmutil user      -> "No semantic conflicts found across 2 integrated branch(es)."  exit 0
```

Because combined "replaces" pairwise CW001/CW002 (v0.3a §3), this is a silent recall regression of `--combined`
vs the pairwise mode on a very common package layout. Fix: in `_resolve`, for a `from P import n` binding where
`P/n.py` or `P/n/__init__.py` exists at the commit, resolve to that module (valid) instead of recursing into `P`;
more generally, when the combined state check returns `unknown` for a reference that pairwise flagged, surface it
(see V3-13) instead of dropping it.

### V3-07 major — pairwise false positive: module turned into a package

`engine.side` (`:120-122`) emits `removed` for every symbol of the old path when the old file is deleted/renamed,
without checking that the same module name is provided by the new path (`m/__init__.py`).

```
mkdir app; touch app/__init__.py; printf 'def f(x):\n    return x\n' > app/m.py; c base
git branch pkgify; git branch user
git checkout -q pkgify; mkdir app/m; git mv app/m.py app/m/__init__.py; c "m -> package"
git checkout -q user; printf 'from app.m import f\n\nprint(f(1))\n' > app/use.py; c use
cw check pkgify user                               -> CW001 [user × pkgify] `app.m.f` ... removed in pkgify   exit 1  (FALSE POSITIVE)
cw check --target main --combined pkgify user      -> no conflicts exit 0   (correct)
```

Fix: when computing `removed` for a deleted/renamed module, diff against the symbols of the same module name at the tip
(whatever file provides it) instead of `{}`.

### V3-08 major — pairwise false positive: submodule re-export dropped from `__init__`

```
mkdir -p app; printf 'from app import util\n' > app/__init__.py; printf 'def h():\n    return 1\n' > app/util.py; c base
git branch cleanup; git branch user
git checkout -q cleanup; printf '' > app/__init__.py; c "drop unused import in __init__"
git checkout -q user; printf 'from app import util\n\nutil.h()\n' > app/use.py; c use
cw check cleanup user                              -> CW001 `app.util` ... removed in cleanup  exit 1   (FALSE POSITIVE: app/util.py still exists)
cw check --target main --combined cleanup user     -> no conflicts exit 0   (correct)
```

`from pkg import name` imports the submodule when `pkg/name.py` exists. Fix: CW001 (pairwise) must not fire for a
removed *package-level* name if the tip of the cause branch still has `pkg/name.py` / `pkg/name/__init__.py` (cheap
`read_file` check, same code V3-06 needs).

### V3-09 minor — `bounded` coverage without a bound

A textual conflict between a branch and the **target** itself (most common CW005) has zero candidate culprits;
`not exact` then adds `max_group` to `limits_hit` (`combined.py:169-170`).

```
printf 'a = 1\n' > x.py; c base; git branch b1; git branch b2
git checkout -q b1; printf 'a = 2\n' > x.py; c b1
git checkout -q b2; printf 'b = 1\n' > y.py; c b2
git checkout -q main; printf 'a = 3\n' > x.py; c main
cw plan --target main b1 b2
  Merge plan into main (2 branch(es)):
    1. b2 — placed before b1: b1 would break x.py (CW005)
  Blocked:
    b1: x.py:1 CW005 textual conflict with main — rebase b1 onto main (conflicts in x.py)
  Coverage: bounded (max_group) — unchecked combinations are not proven safe.        <- nothing was bounded
```

B1: `bounded` only when a limit was hit. Fix with V3-04: the target is a culprit (`culprits: [<target>]`, exact),
and only add `max_*` when `len(candidates) > 6` or the 1..3 enumeration was exhausted with ≥ 1 candidate.

### V3-10 minor — stacked branches reported twice by `check --combined`

D8: shared changes are attributed to the earliest branch only. `plan` filters this (`planner.py:80-84`) but
`check --combined` does not (`consolidate` keys include `branch`).

```
(base: app/m.py with f)  A: adds app/use.py using f;  B = A + another commit;  rm: removes f
cw check --target main --combined rm A B
  app/use.py:1 CW001 error branch=A culprits [rm]
  app/use.py:1 CW001 error branch=B culprits [rm]        <- same use site, 2 errors in "summary"
```

Fix: move the identity-based ancestor attribution into `analyze_combined` (needs `is_ancestor` once per pair).

### V3-11 minor — state CW004 culprits

Three branches M1 (`0002_add_a.py`), M2 (`0002_add_b.py`), M3 (`0003_add_c.py`) on a Django app. `plan --format json`:
blocked finding for M2 has `"culprits": ["M1","M2","M3"], "culprits_exact": true` while the step reason of the same
report says `culprits M1, M2` and `check --combined` says `[M2 × {M1}]`. `_migration_findings` sets
`tuple(sorted(labels))` and `True` unconditionally (`planner.py:37-38,44-45`); `branch` is `labels[-1]` (arbitrary).
Fix: derive culprits from the branches whose added files collide (path → branch map from the summaries).

### V3-12 minor — `migrations` holds every added `.py`

`engine.py:142-145` stores the source of every added Python file under `BranchSummary.migrations` (name and
PLAN §12.1 say "added migration path → source"). A branch adding 300 vendored files (12 300 lines) produced a
260 KB cache entry (`.git/crosswire/cache/v1/*.json`, measured); the prefilter clause
`left.migrations and right.migrations` (`engine.py:239`) is true for any two branches that add any new `.py`
(e.g. tests), so semantic rules run for pairs that cannot interact. Fix: store only paths matching the Django/Alembic
patterns (`cw004._DJANGO` / `versions/`), keep a version bump of the cache schema.

### V3-13 minor — "complete" does not say what was not analysed

`unknown` references (third-party modules, star-import chains, depth > 5, cycles, syntax errors) are dropped
silently at `combined.py:185`/`:244`; combined output is "No semantic conflicts found …" with
`"coverage": "complete"` even if every reference was unresolved (e.g. V3-06). VISION §1 and V6/V7 and QUALITY Q1.8
require coverage gaps to be reported. Not a v0.3 plan item, but `coverage` is a published v0.3b key whose
meaning ("complete") is then overstated. Suggest adding `unresolved: <count>` (+ per-reason counts) to `limits`
in v0.4 diagnostics, and not using the word "complete" for resolution coverage.

## Checked and found correct

- **Read-only guarantee** (PLAN §0, QUALITY §5): with a dirty worktree (staged + unstaged + untracked changes) ran
  `check`, `check --combined`, `plan` (cache and `--no-cache`). `HEAD`, `HEAD` symref, `for-each-ref`, index checksum,
  `git status --porcelain=v2`, every worktree file checksum and every non-object file under `.git` (except the cache
  dir) were byte-identical before/after. Only new loose objects and `.git/crosswire/cache/v1/*.json` are created.
- **Exit codes / streams:** unknown ref → `crosswire: error: unknown revision: nope`, exit 2, empty stdout;
  `--combined` without `--target` → exit 2; findings with errors → 1; warnings only → 0 (`resolved_by`).
- **Acceptance scenarios (v0.3a §5):** conjunctive removal → one `CW006 [C × {A, B}]`, culprits exact, decoy D not
  involved, pairwise silent (as specified); `DCBA` permutation → identical finding; fixed-by-third → one `CW001`
  **warning** with `resolved_by ["B"]` (pairwise still `CW001` error); textual skip → `CW005` with `culprits` and
  `skipped` entry; permuting order changes only which branch is skipped.
- **Plan (v0.3b T9/B1):** `plan A C B` on fixed-by-third places `B` before `C` with the explanation
  "…resolves CW001 of C"; conjunctive case places A, B, D and blocks C with culprits; state CW004 blocks the second
  Django migration; `blocked[].hint` for CW005 ("rebase … onto …"); JSON keys of plan v2 (`steps[].reason`,
  `blocked`, `contained_in`, `summary`, `coverage`, `limits`) match PLAN + B1; step ordering is deterministic.
- **Determinism / cache:** `--no-cache`, cold cache and warm cache produce byte-identical JSON for pairwise,
  `--combined` and `plan` on the 4-branch scenario; repeated runs identical (sorted keys, canonical sort).
- **Virtual integration (D1):** fixed identity/date/message, `commit.gpgSign=false`, no refs written, memoised by
  `(previous, branch)`; a textual conflict skips the branch and integration continues.
- **Conservative resolution:** third-party imports (`unknown` at the tip), references already broken at the branch tip,
  locally rebound names, and calls with `*args/**kw` do not produce findings; guarded/conjunctive definitions count as defined.
- **Wire contracts:** pairwise `version: 1` JSON unchanged; combined `version: 2` keys match v0.3a §4 (+ B1
  `coverage`/`limits`); SARIF/GitHub formats carry `culprits`; `plan` rejects `--format sarif|github` as specified.

## Not verified / limits of this review

- Python 3.11 behaviour (only 3.12 and 3.14 interpreters present). On 3.11 `ast.parse` raises `ValueError` for NUL
  bytes (not `SyntaxError`) — same uncaught-exception class as V3-01 but not reproduced here.
- Test suite at `HEAD`: `uv run --offline pytest -q` from a `git archive` copy (Python 3.14): **288 passed in 334 s**.
  None of the findings above is covered by an existing test — all of V3-01…V3-08 pass the current suite.
- Odd git states (bare repo, shallow clone, submodules, symlinked `.py`, linked worktrees) were not exercised.
- Timings were taken on a shared machine while Terra/Sol were also running tests; treat them as order-of-magnitude.

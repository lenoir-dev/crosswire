## Details

### E4-01 blocker — the holdout repositories can be recovered from public files

`eval/screen.py` (in the shared workspace, readable by Altair) contains the complete `CANDIDATES` list (32 `owner/repo`
names). `v04-screening-summary.json` says: 34 screened, 28 full checker runs, **7 green**, 5 development, **2 holdout**;
`eval/development-selection.json` names the 5 development repositories. The two private repositories are therefore
exactly the green candidates that are not in the development selection. Running `eval.oracle.run` (pinned) over the listed
repositories reproduces the screening in minutes; nothing secret is needed. `eval/README.md:21-24` states the opposite
("the original full screening pool … remain outside"). This breaks Q1.5 ("Terra/the implementation never read that
path" — here nothing needs to be read) at repository level: the implementer could tune against the *source* of the
holdout repositories, and the mutation families are only protected by secrecy of the private recipes.
I did not run the deduction, to avoid learning identities.
Fix: move `CANDIDATES` and per-candidate screening rows to the private directory (publish aggregate counts only, and
not "exactly 2 / 7 green"); treat the current two private repositories as **exposed at repository level** until the architect
decides otherwise (cheapest sound option: re-screen with a *new* candidate list kept private, re-seal, then evaluate).

### E4-02 major — isolation is honour-system

`~/.crosswire-holdout` is `drwxr-xr-x`, owned by the same user that runs the Codex workers and me; `chmod(0o600)` on the result
file (`run_holdout.py:52`) changes nothing for a same-user process. There is no OS or sandbox barrier; the guarantee in
`TEAM.md` is purely procedural. Suggested: deny the path in the Codex worker sandbox configuration (or move the directory to a
separate OS account / an encrypted volume whose key only Deneb's run uses), and record an access-time audit before and after the
final run. Also define the architect's audit protocol: root-cause *categories* may flow to Altair, never case-level hints
(`publish.py:82-84` says the architect "can audit labels" — that audit is itself a leak channel if followed by case-specific fixes).

### E4-03 blocker — the holdout cannot answer anything, and it can only be run once

`v0.4.md`: holdout = **6 positives / 18 controls**, 2 repositories. Under Q1.7/M1 §7 every cell (<20 predictions or <20
positives) is "insufficient data", `clustered()` on 2 repositories returns an interval anyway (proved: two toy repos →
`precision [0.667, 1.0]`, 3 possible resamples), and the development split itself has 24 positives spread as PY-1 5 / PY-2 4 /
PY-3 2 / PY-4 13 (all supported-type cells < 20). `run_holdout.py:43` refuses a second run, so the single execution is spent on a
measurement that cannot pass or fail a gate, and the per-case root-cause audit that QUALITY §3 requires will expose its cases to
the team, i.e. burn it for v0.5+. A crashed run (exception → private failure file) is repeatable, so the "once" rule is also
weaker than stated.
Decision needed from the architect: (a) enlarge/reseal the holdout (≥ 5 repositories, ≥ 20 positives per reported cell, see E4-01/08)
**before** the first evaluation — allowed because no holdout measurement has happened yet — or (b) do not run it in v0.4 and publish
the development split plus live-PR noise only; reserve the holdout for the first release whose sample size is sufficient.

### E4-04 major — the seal is not anchored

`git ls-files` shows `docs/validation/holdout.sha256` is **untracked** (so is all of `eval/`); only `matching.md` is committed.
QUALITY §2 requires the hash "committed before any tuning"; today only file mtimes (18:48) order the events, and the file is
owned by the party that is measured. The hash covers `v04-sealed-manifest.json` only. `measure.evaluate` runs the detector on
`case["path"]` with the *branch names* `A`/`B` and reads prediction sites from the worktree (`measure.py:30-31,48-49`), so
moving a ref or editing a private worktree after sealing changes the measurement but not the hash. Also not sealed: `eval/*.py`,
`policy.json`, `matching.md`.
Fix: architect commits `holdout.sha256` (+ `policy.json`, `matching.md`, a combined hash of `eval/*.py`) now, before the R1 source
changes land; `run_holdout` asserts `git rev-parse A/B == tips`, `HEAD == integrated`, clean worktree, and writes the eval-code hash
into the aggregate.

### E4-05 major — detector failures vanish from recall (proved)

```
evaluate(<2 required_keyword positives>, detector=<script that exits 2>, src)
  -> rows eligible: [False, False], exclusion "detector execution error"
  -> aggregate: tp/fp/fn = 0/0/0, recall None, unlabelled_cases 2
```
A detector that crashes on a positive is recorded as an "unlabelled case" (`measure.py:35-37`), i.e. it leaves the recall
denominator exactly where an oracle/environment failure would. Those are different: oracle failures are unlabelled by Q1.1, a
crash of the system under test is a miss (positive) or an unscored failure that must be reported next to every metric. Conversely an
exit-1 traceback (the V3-01 shape) makes `json.loads` raise (`:38`) and aborts the whole holdout run. Fix: a `detector_failure` outcome
counted as FN for positives and published as its own count; a per-case timeout is a failure row, not a global abort.

### E4-06 major — type and rule are taken from the case, not the finding (proved)

`predictions.append({"type": case["type"], …})` (`measure.py:58`) means the "supported type" component of the M1 identity is always
equal; and `row["rule"]` (`:75`) is `CW001` if the case type is PY-1..3 else `CW002`. With a fake detector that reports a **CW001**
"removed" finding at the exact call site of a PY-4 `required_keyword` positive: `tp/fp/fn = 1/0/0`, bucketed under CW002. Consequences:
wrong-rule detections count as TP, per-rule precision/recall are really per-type, CW006 (and CW001-vs-CW006 culprit confusion) is
never separable, and the table in `v0.4.md` shows CW006 as an always-empty row regardless of what the detector emits. Fix: key predictions
by the rule the finding carries, map rules to supported types (CW001→PY-1/2/3, CW002→PY-4, CW006→PY-5 and multi-branch PY-1..4), and
count mismatches as FP + FN.

### E4-07 major — 60 % of predictions are outside the oracle

`checked` (`measure.py:43-46`) keeps only findings inside the production roots or the consumer; all others are "unlabelled". In the
development run: 36 of 60 predictions (30 CW001, 6 CW002), all in `tests/` (25 of them on `module_move` positives), **7 on coordinated controls**. They are probably true breakages (A/B rename the function but never update `tests/`), which also means the
claim "controls are compatible changes" and "both tips are green" hold only for the pinned production roots — repository tests are
broken in the integrated state of every rename-type control. The harness therefore (a) never learns whether those predictions are
right, so any FP among them is invisible to precision, and (b) understates TP. Fix: either run the oracle over the tests too
(test dependencies are already installed in the checker environment) or make A update tests as it does production callers;
until then publish "precision on oracle-covered predictions (40 %)" in the headline, not "precision".

### E4-08 major — the corpus is easy and narrow

All positives use one consumer template (`import <module> as module; module.<f>(cast(Any, None), …)`, `corpus.py:80-99`) — never
the dominant real form `from m import f; f(x, y=…)`; only module-level functions are mutated (no classes, variables, re-export
chains beyond one hop); every case has exactly 2 branches, so CW006/PY-5 (listed as supported in `policy.json`) has **zero** cases and
attribution cannot be wrong except by naming the other branch: "attribution 100 %" (20/20) is true by construction (`measure.py:53`,
`corpus.py:344`: `attribution_oracle` is the constant `True`; for |S| = 1 this is equivalent to the M1 §2 trial result, but it is never
recorded as a trial and |S| ≥ 2 is never exercised). The three control families (unrelated comment edit, optional keyword, identical
rename) cannot trip a conservative detector, and none resembles the false-positive classes found in v0.3 (star-import / `__getattr__`
modules, module→package, submodule re-export dropped from `__init__`, third-party/guarded imports). The development split already shows
the effect: detector 24/24 on real conflicts, so it cannot discriminate good from bad versions. Fix: add hard-negative families derived
from `docs/reviews/v0.3-vega.md` V3-02/03/06/07/08 and PLAN-v0.4 R1 (these must exist in the holdout too — another reason for E4-03(a)),
a `from m import f` consumer form, a 3-branch conjunctive family for CW006, class `__init__` signature changes (PY-4 as written).

### E4-09 major — PY-2 is structurally unmatched

For `module_move`, Pyright reports `reportMissingImports` at the import line (line 2) while the detector reports the later attribute use
(line 5, symbol = function). `evaluate` maps the oracle symbol to the module (`measure.py:69`), so identity never matches: each of the 4
PY-2 positives counts 1 FP + 1 FN (`v0.4.md`: all four development FP/FN). The three real-conflict dimensions are right in every one;
the 20/4/4 headline (precision 83 %, recall 83 %) is therefore mostly this artefact. `handoff.md` proposes to keep M1 unchanged; I
disagree for the one-shot run: the rule was pre-registered but demonstrably unintended (M1 §1 says "line shifts allowed"), PY-2 recall
would be 0 and every PY-2 holdout case an FP, and any later correction is forbidden as post-hoc. Fix before any holdout run: architect
amendment M2 — for `reportMissingImports`, match on (consumer file, module) accepting any prediction whose module prefix equals the
missing module, one prediction per root cause.

### E4-10 major — frozen policy does not match what ran

`eval/policy.json` (`frozen_before_labels: true`) lists development mutations `remove_attribute, rename_attribute, required_positional,
required_keyword, unknown_keyword, too_many_positional`. `cases.json` contains `remove_attribute 5, required_keyword 5, module_move 4,
unknown_keyword 3, required_posonly 3, remove_reexport 2, too_many_positional 2`; `rename_attribute` and `required_positional` never ran,
`required_posonly`, `module_move`, `remove_reexport` are not in the frozen list (r2 amendment covers the first two only). Also
`decisions-log.md` row 5: development "compatible" controls were redefined (optional keyword) *after* the private labels were sealed —
"existing private labels stay sealed" — so holdout controls are the older, weaker documentation-only kind. Holdout precision is thus
measured against easier controls than the development split; the report must say so. Fix: re-issue `policy.json` as an amendment with
timestamps and hashes of each generator revision (r1/r2/r3 are only in `development-policy-r2.json` + flow counts).

### E4-11 minor — intervals

`aggregate()` gates on Wilson only (point ≥ 95 % and Wilson lower ≥ 90 % — matches Q1.7 literally, test-covered). The repository-clustered
interval is computed for any ≥ 2 repositories and never gates; with correlated cases (3 controls per candidate) Wilson is
over-optimistic. Suggest: gate lower bound = min(Wilson, clustered) and clustered "insufficient data" below 5 repositories.

### E4-12 minor — aggregate guard

`assert_aggregate_only` rejects forbidden **keys** and `.crosswire-holdout/`/`github.com/` in **string values**, but dict *keys* such as
`exclusions[...]` and `candidate_exclusion_counts[...]` come from private free-text `exclusion` strings and are never scanned; with 6
positives, per-rule and exclusion counts essentially reveal individual case outcomes. Use a fixed vocabulary of exclusion keys and
suppress cells with n < 5 in the public aggregate.

### E4-13 minor — reason-category mismatches

Where the oracle emits two diagnostics for one call (`itsdangerous-008`: "Argument missing" and "No parameter named"), `evaluate` keeps
`errors[0]`; 2 of 6 reported CW002 reason mismatches are only this (the other 4 are real positional-only vs positional/keyword
disagreements). Compare against the *set* of oracle categories for the root cause.

### E4-14 minor — reproducibility

Node (used by the `pyright` wrapper via `nodeenv`) is not pinned; `v04-oracle-requirements.txt` has no hashes; `cases.json` stores absolute
`/tmp/...` paths and checker commands; `replay` needs network and a fresh clone; mined history takes the latest 5 merges per repository
(not seeded; 8 candidates, 7 controls, 0 positives — fine as labelled, but it says nothing about recall); `corpus.create_repo` mutates
`os.environ` globally (dates).

## Checked and found correct

- **Metrics vs matching.md + M1:** one-to-one greedy matching (`metrics.match`), detection (type/path/symbol/occurrence) separate from
  attribution (share of detection TPs with oracle-confirmed culprits), CW002 reason category not required for detection and counted
  separately, unlabelled counts and share published per metric. Wilson formula correct; gate logic = point ≥ 95 % **and** Wilson lower ≥ 90 %
  (precision), point ≥ 80 % (recall), any cell with < 20 predictions or < 20 positives "insufficient data" (unit-tested); percentile bootstrap
  resamples whole repositories (never cases) with fixed seeds (`17042026`, `9042026`, 2 000 replicates).
- **Oracle:** the same `run()` and the same config (`policy.json` oracle block, `include = roots + consumer`) is used for target, A, B and
  integrated; version string and `filesAnalyzed`/`errorCount` consistency checked; timeouts, non-JSON, exit-code inconsistencies →
  `unlabelled`, never negative (parametrised tests); positives require green target + both tips, textually clean `merge-tree`, and a *new*
  consumer diagnostic of a supported rule; controls require a green integrated state; labels never consult the detector.
- **Corpus integrity (development):** 96/96 case repositories have `HEAD == integrated`, `A == tips.A`, `B == tips.B`; the seeded 10 % audit
  sample and all four FPs are prepared; every rejected generator attempt is retained (`v04-development-flow.json`,
  `v04-development-exclusions.json`: r1 77, r2 10, r3 8 rejected positives vs 24 accepted — transparent, but note the 22 % acceptance rate).
- **Read-only guard:** `evaluate` snapshots HEAD, refs, `.git/HEAD`, index and every worktree file around the detector run and asserts equality;
  source files are hashed before/after the run; `--no-cache` avoids writing into case repositories.
- **Leak checks:** no `~/.crosswire-holdout` content or path appears in tracked/untracked workspace files except in guard messages and docs; no
  non-development repository clone exists under any `/tmp/crosswire-v04-*` directory; `v04-oracle-requirements.txt` is fully explained by the
  five development repositories plus tooling (no private-specific dependency); the published results, gallery and exposure list name only
  development/live-PR repositories; `run_holdout.py` refuses a second *successful* run, checks the manifest hash before loading labels and
  prints only aggregate fields. `tests/test_eval.py`: 19 passed (run offline).

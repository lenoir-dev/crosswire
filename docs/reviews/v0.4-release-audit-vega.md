## 1. Label audit (QUALITY §3, matching.md + M1/M2)

### Method

- **Population and sample.** 179 eligible development cases (`eval/development/cases.json`,
  `eligible: true`). Random sample of **20** with Python `random.Random(20261118).sample` over the
  sorted ids (10 % of 179 = 17.9, so at least 18). It is disjoint from Deneb's prepared
  sample except for 3 ids. Because that sample holds only 6 positives, I added **10 more positives**
  with `random.Random(7)`. In total 30 cases: **16 positives** (PY-1 ×6, PY-2 ×2, PY-4 ×7, PY-5/CW006 ×1) and 14 controls. The positives span
  both strata (6 historical, 10 scaffold) and all 3 repositories (blinker 7, sniffio 5, trove-classifiers 4).
  The ids and outcomes are in
  [v0.4-release-audit-vega-sample.json](v0.4-release-audit-vega-sample.json).
- **Independent re-derivation.** For each case I cloned the case repository, rebuilt every subset
  integration **myself** with `git merge-tree --write-tree` plus `commit-tree` (the oracle's recorded
  `integrated` commit is not used for the label), archived each state, and ran the pinned
  `pyright 1.1.407` (Python 3.14.8, basic mode, the three report rules from `eval/policy.json`, same
  include scope: production roots, test directories, probe consumers) from my own driver script. Label
  rule: positive iff the full integration fails and the target plus every proper subset passes.
  Minimality: for 2-branch cases, T, A and B pass and A+B fails. For the 3-branch CW006 case, all 7 proper
  subsets pass, so culprits `{A, B}` on target `C` are exactly minimal.
- **Match check.** Current `crosswire check --combined` (and pairwise) with `--no-cache` against each case,
  compared with my oracle diagnostics per matching.md: rule/type from the finding, use-site file and
  symbol, culprit set, one-to-one, M2 PY-2 on (module, file).
- **Tree check.** My merged tree equals the recorded integrated commit's tree in 30/30 cases (no hidden
  textual conflict, no hand-edited integration).

### Result

| Oracle statuses: target, A, B green on all 30 | yes |

| Culprits exactly right and minimal in my subset table (incl. CW006 `{A,B}` on C) | **16/16** |
| Controls: oracle clean and 0 crosswire findings (combined and pairwise) | **14/14** |

The labels and the 0 FP / 0 FN claim reproduce. Caveats on what this audit can and cannot detect:
I re-implemented the driver but used the same policy file, pyright version and scope design as the
apparatus. It can catch case-construction, merge, minimality and matching errors, but not a shared blind
spot in the policy itself, such as a rule that pyright basic never reports. 10 of the 16 positives are
the repeated scaffold mechanisms (e.g. `crosswire_probe_000.api.f` appears in several repositories), so
the effective independent n is smaller than the case count, as the report already says.

### The 4 CW002 reason-category disagreements

Confirmed as a categoriser limitation, not a detector error. `blinker-016`, `r2-public-0032`,
`-0076` and `-0120` all consist of `def f(value, /)` called as `f(value=1)`. Pyright's message is
the generic "Expected 1 more positional argument", which the frozen categoriser maps to null. The
detector's "positional-only" is the correct category. I re-ran 0032 and 0120 myself and got the same
message. The report's explanation is accurate. No change needed. Optionally, recategorise "Expected N more
positional argument" at v0.5, with a declared amendment.

### The 49 exclusions (sampled 9, all rightly ineligible)

All 49 are `oracle-ineligible`. I re-ran the oracle on 9 of them (seed 20261118: 4 hyperframe, 4
itsdangerous, `blinker-020`):

- hyperframe (4/4): the **target itself** fails with 40 pre-existing pyright errors in `tests/`
  (`Cannot access attribute "data" for class "Frame"` etc.).
- itsdangerous (4/4): the target fails with 4 pre-existing errors (3 overload mismatches in
  `test_serializer.py` plus `Import "freezegun" could not be resolved`).
- `blinker-020`: target and B green, but A alone is non-green (`tests/test_symbol.py` still imports the
  removed `blinker._utilities`), so the case is not a clean positive.

Under matching.md rule 1/2 (green target and tips) these exclusions are correct, and the report's
description (20 + 28 + 1) is accurate. See M2 for what the exclusions hide and m4 for the policy
consequence.

### M1: live-PR "0 noise" under partial coverage (Major)

`v04-live-prs.json`: coverage is **partial in all three repositories**
(httpx: 170 unsupported + 2 splatted sites; django: 2,688 + 82; flask: 1,168 + 19). v0.4.md reports
"0.00 flags / 100 pairs" and "pallets/flask 0.00" in a table with no coverage column and no sentence
saying the replays were partial. A reader will take zero as "clean", when it partly means "much of the
changed code is unsupported dynamic Python". The text does say the result cannot establish precision,
which is good, but it does not give the reason a reader needs.
**Fix (wording only):** add a Coverage column (partial ×3) and a sentence: "all three replays are partial;
zero flags means no supported-construct conflict was found in the analysable part, not that the PRs are
conflict-free."

### M2: the unlabelled-share statements are vacuous (Major)

v0.4.md lines 56 and 101: "outside-oracle-scope/unlabelled predictions: 0/44 = 0.00 %" and "There are no
unlabelled emitted semantic findings to list." In `v04-development-results.json` the 49 ineligible rows
have **no detector report at all**: the detector was never run on them. The 0 % is therefore true by
construction (eligible means fully oracle-covered). I ran the current detector on 9 of the 49:

| Excluded case | Combined findings |
| --- | --- |
| hyperframe ×4 (unrelated/compatible controls) | 0 |
| itsdangerous-000, -012 (positives) | 2 each (CW001 / CW002) |
| itsdangerous-024 (positive) | 2 (CW001) |
| itsdangerous-007 (coordinated control) | 1 (CW001, `base64_encode`) |
| blinker-020 (positive) | 2 (CW001) |

5 of the 9 produce 9 findings in total. On inspection they are **not false positives**: the pyright diagnostics in A,
B and A+B confirm the broken import (e.g. itsdangerous-007: `"base64_encode" is unknown import symbol`
in `tests/test_itsdangerous/test_encoding.py`, which neither branch updates), but they are unlabelled and
sit outside every denominator. The honest statement is "predictions on excluded cases were not
measured". **Fix:** either run the detector on the 49 and publish the emitted findings as unlabelled
(M1 rule 4 asks for the unlabelled share next to each metric), or reword both sentences to say the
share is undefined because the excluded cases were not run.

### B1: package metadata (Blocker; PyPI uploads are immutable)

`pyproject.toml` has only name, version, description, license, requires-python and dependencies.
The built `PKG-INFO` has no `Description` (no `readme = "README.md"`), no `Project-URL`, no
classifiers, no authors, no keywords. The 0.4.0 project page on PyPI would be a blank body with no link to the
repository, and a published version cannot be amended; fixing it costs a 0.4.1.
**Fix before tagging:** add `readme = "README.md"`, `[project.urls]` (Homepage/Repository/Issues),
`classifiers` (Python 3.11–3.14, Apache-2.0, OS independent, "Topic :: Software Development :: Version
Control :: Git"), `authors`, `keywords`; rebuild and check `twine check dist/*` (or `uvx twine check`). Also
confirm the PyPI name `crosswire` is free before the first upload.

### M3: sdist contents and local paths (Major)

The sdist is 467 KB compressed, 4.8 MB unpacked: `docs/` (70 files, including internal team and review
notes), `eval/` (32), `tests/` (32), `benchmarks/`, `.github/`, `uv.lock`. It contains **940 occurrences of
`/Users/<name>/…`**: `eval/development/cases.json` (774), `docs/validation/v04-development-results.json`
(165), `docs/validation/httpx-target.json` (1). That is the owner's local account name inside a public
artifact. No other personal data found in the sdist (no email). The wheel is clean (29 modules plus 3
schemas plus LICENSE).
**Fix:** `[tool.hatch.build.targets.sdist] include = ["src", "tests", "README.md", "LICENSE", "pyproject.toml"]`
(or `exclude` for `docs/`, `eval/`, `benchmarks/`, `.github/`); and rewrite or tokenise the absolute paths in
the committed eval JSON before the GitHub push (the apparatus already uses `${CACHE_*}` tokens
elsewhere). Separately: the git history to be published carries a personal commit author email; please
confirm that is intended.

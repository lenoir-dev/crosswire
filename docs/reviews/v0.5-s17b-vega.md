## B1 — squash versus rebase: a single-parent commit cannot prove "squash", and the design gives no other evidence (blocking)

**Design text.** "When `merge_commit_sha` identifies its single-parent squash integration commit … `D = that commit's parent`";
"a single-parent commit alone does not distinguish squash from the last commit of a rebase merge; ambiguous merge-method
evidence remains unresolved"; the test list asks for "ambiguous merge-method evidence". Nowhere is the evidence defined.
An implementer has two choices: treat every single-parent commit as a squash (wrong for rebase merges) or treat every one
as ambiguous (the squash branch never fires). Neither can be tested.

**What the graph shows** (local experiment, scratch repo; PR of 3 commits, default branch advanced meanwhile):

```
squash : 03a6199 p=c932da5 (1 new commit, author date = squash time, subject "squash (#1)")
rebase : dc5eafe p=d0ab81a / d0ab81a p=cfe547e / cfe547e p=c932da5   (3 commits, author dates 01-03, 01-02, 01-01 preserved)
patch-id of the 3 PR commits:      921527f986c7  d532f052b535  151d0d05f0aa
patch-id of the last 3 on rebase:  921527f986c7  d532f052b535  151d0d05f0aa      (identical)
patch-id of the squash commit:     7c6524512ca8                                (matches none)
git cherry <squash> <pr>  → + + +        git cherry <rebase> <pr> → - - -
```

So for a PR with `n` commits (`commits` in the PR detail), a rebase merge leaves `n` consecutive first-parent commits
ending at `C = merge_commit_sha`, preserving author, author date and subject and (unless conflicts were resolved)
patch-ids; a squash leaves one commit that matches none of them. Consequences:

1. **`n == 1`: squash and rebase are indistinguishable by graph and equivalent for the anchor** — `C^` is the correct
   pre-PR default state either way. State this as the rule: n=1 needs no merge-method evidence.
2. **`n ≥ 2`:** classify from the PR commits, not from `C` alone:
   - *rebase proven* if the last `n` first-parent commits ending at `C` equal the PR commits one-to-one by (author, author date, subject) **or** by `git patch-id --stable`;
   - *squash proven* if `C` is single-parent, **no** commit in `C~(n-1)..C` matches any PR commit by those keys, and `git cherry C pr-range` reports `+` for every PR commit;
   - anything else (partial matches, conflict-resolved rebases whose patch-ids changed) → `default-anchor-unresolved`.
3. **Rebase merges need not be thrown away.** With the match in 2, `D = C~n` (the parent of the first rebased commit) is exactly as provable as the squash anchor. Keeping them unresolved is acceptable for a first round (it lowers yield), but then say so and make the classification above the *only* thing that separates "unresolved" from "squash": a classification that can fail is the point.
4. **Do not rely on commit-message conventions** (`(#N)`, "Squashed commit of …"): they are configurable and typed by humans. (*Unverified:* GitHub's default squash message carries the PR number; the design should not depend on it either way.)
5. Add tests (all synthetic, as the design already plans): n=1 squash and n=1 rebase both accepted with the same `D`; n=3 squash accepted; n=3 rebase → unresolved (or accepted with `D=C~3` if item 3 is adopted); n=3 rebase with a conflict-resolved commit (patch-id changed, author/date/subject preserved) → the key rule must still classify it, or leave it unresolved, never squash; a "squash" whose message copies a PR commit subject must not be called a rebase; `C` off the first-parent chain → unresolved.

Also record, per pair, which rule fired (`anchor_method ∈ {merge, squash-n1, squash-proven, rebase-proven, unresolved}`) so a reviewer can audit the 10% sample.

## B2 — head contamination has no procedure (blocking)

**Design text.** "Reject identical/ancestral heads and cross-contamination … Require graph evidence; unresolved
squash/cherry-pick equivalence is unlabelled." This is the check that keeps the two-branch experiment honest, and it
names no operation. Three concrete holes:

1. **Later PR contains the earlier PR's integration.** If B was updated from the default branch after A merged, `C` (A's
   integration) is an ancestor of `H_B`, and `B_B = D`/later than `D`. The design never states the test `C ∉ ancestors(H_B)`.
   For a true merge `C`, `H_A ∈ ancestors(H_B)` is the equivalent; for a rebase merge it is `C` (the last rebased commit).
   This matters most: B is the **later-ending** PR, and many repositories require branches to be up to date before merge,
   so *merged* later PRs are the ones most likely to contain A.
2. **Stacked PRs / shared PR-only history.** `H_A` and `H_B` can share commits that are on neither default branch nor the
   bases (B branched off A's branch; A later force-pushed, so `H_A` is not an ancestor of `H_B`). Test:
   `merge-base(H_A, H_B)` must be an ancestor of `D` (on default); equivalently `rev-list H_A H_B ^D` has empty intersection
   of `rev-list H_A ^D` and `rev-list H_B ^D`.
3. **Cherry-picked or rebased copies.** Content of A already inside B without ancestry. Test: the `git patch-id --stable`
   sets of `B_A..H_A` and `B_B..H_B` must be disjoint; a non-empty intersection → `contaminated-heads`, unlabelled.

Also state that the contamination test runs **before** the integration, uses only graph/patch-id evidence, and is
independent of any checker output (so it cannot be tuned after seeing results). Add the three cases to the synthetic-graph
test list, plus the negative (two unrelated PRs with equal-looking changes are not flagged by patch-id).

## N1 — evaluation order, the request ceiling and exclusion stages (non-blocking, must be settled before freeze)

- **Ceiling.** Requests needed per candidate PR: list pages (shared), 1 detail, ≥1 `files` page, ≥1 `timeline` page, plus
  1 commit detail per anchor. Evaluating *every* PR of every overlapping pair "after the fixed filters" then sorting is
  hundreds of PRs per repository; 1,500 GETs across 8 repositories cannot cover it. If the ceiling hits mid-way, the
  candidate ledger — and therefore the hash-ordered top 20 — depends on fetch order, which breaks the "reviewer can reproduce
  the cap" promise.
- **Fix (keeps the selection rule unchanged):** enumerate overlapping pairs from list data only (created/closed/merged
  timestamps), order them by the hash, and **walk that order**, evaluating the metadata filters (detail, files, timeline)
  lazily until 20 pairs pass or the order is exhausted. This selects exactly the same set as eager evaluation (the filters
  are metadata, the order depends only on `(repo-id, A, B)`), costs about `2.2 × 20` PRs per repository, and makes the
  ceiling a statement about a deterministic prefix. Record the rank of every evaluated pair and every filter outcome.
  Rough fit: 8 × ~45 PRs × 3 GETs ≈ 1,100 plus list pages and anchor lookups — inside 1,500 only with lazy evaluation.
- **Exclusion stages are inconsistent.** One paragraph removes pairs with "missing/inconsistent timestamps" from the
  cohort *before* ordering (they do not consume the cap); another keeps "incomplete lifecycle evidence", "reopened" and
  "metadata-uncertain" as *selected-but-unlabelled* (they do consume it). Both are outcome-blind, but the report's
  arithmetic needs one table: for each exclusion, the stage (before ordering / after ordering), whether it consumes a slot,
  and which data it needs. With lazy evaluation, the natural rule is: only the list-derived overlap is pre-ordering;
  everything else is evaluated in order and consumes the slot.
- **Python-touch from list data is not possible** (list items carry no file counts): confirms the lazy approach.

## N2 — timestamp pagination stop rule (non-blocking)

The rule is directionally valid: if every closed PR satisfies `updated_at ≥ end_i`, a descending-`updated` list can stop at
the first PR with `updated_at < 2022-01-01` (a whole page is not needed, but is harmless). Moving items cannot be skipped:
`updated_at` only grows, so a concurrent update moves a PR to the front and the only effect is a duplicate. Gaps:

1. **The tail is never validated.** The check `updated_at ≥ end_i` runs only on the PRs retrieved; PRs beyond the stop
   point cannot be tested. (*Unverified:* imported or mass-edited repositories may violate it; I did not query any.)
   Mitigation: after the first sub-bound item, read at least one further full page and record the number of violations
   (`end_i ≥ bound` among items with `updated_at < bound`); any violation → continue to the end or declare incomplete.
2. **Reopened PRs currently open are absent** from `state=closed`. A PR closed inside the window and reopened later (still
   open at collection) never enters the universe and is not counted as an exclusion. Count them with a second listing
   (`state=open`, filtering `created_at < cutoff`) or state the hole in the limitations.
3. **Cutoff drift.** `collection_cutoff` is fixed, collection happens later; a PR closed before the cutoff but reopened and
   re-closed after it carries a post-cutoff `end_i` and is dropped (state it). Set the cutoff ≤ collection start so this is
   the only drift.
4. Record the final page's `Link` header and total pages per repository, so "complete" is checkable.

## N3 — seeded hash-order contract (non-blocking)

The contract is exact enough: numeric repository ID, canonical decimals, `A < B`, UTF-8, literal `|`, no newline, digest
bytes ascending, numeric tie-break. Confirmed properties: order-independent of input, stable across repository renames,
no dependence on outcomes. Add to the policy:

- **Test vectors** (SHA-256 of the exact bytes): `s17b-v1|123456789|4|5` →
  `91fbad73416315bd6360c6a6a91935eff18dc9fbdcc0570f30f2405f63486df4`;
  `s17b-v1|1|1|2` → `b6da358de0571c50d09606c27f6035a34683751287fe297c8aa2c5baf074ce10`;
  `s17b-v1|1|2|3` → `20ac85bfa6ed7b2292f5327fce2f207647775a8a0957053997bf6d7a52293322`.
  Include a "leading zero / extra whitespace / uppercase hex" negative test.
- State that the seed string is public and fixed and that **changing it is a new preregistration**, not a retry.
- **PR reuse.** Hashing over *pairs* weights a long-lived PR by how many partners it has (a PR open for a year appears in
  many pairs). Report the number of distinct PRs, the maximum pair count per PR, and the cluster-level effect; consider a
  deterministic cap on pairs per PR (hash order keeps it outcome-blind) only if the ledger shows heavy reuse — never decide
  after seeing labels.

## N4 — M3 reuse: both checks sufficient, small over-exclusion (non-blocking)

Sufficiency argument:

- Check 1 (`delta(B_i → H_i)` empty) is the "green on its own base" condition of D-Nat2. When `B_i == L` it duplicates the
  M3 tip condition for that PR; when `B_i < L` it is a distinct check and is required.
- Check 2 (frozen `label(L, {A_L, B_L}, I)`) rejects errors from normalising a head onto `L` (default drift ∩ PR change)
  and then defines positives as errors absent from both normalised tips. Together they cover: PR-red-on-own-base, red-after-
  normalisation, and new-in-integration.
- Leave-one-out minimal attribution uses `A_L`/`B_L` as the one-branch states, which are exactly the states the label
  compares against; consistent.

Over-exclusion (acceptable, document it): a PR red on its own base but green after normalisation onto `L` (the fix arrived
in default drift) is excluded by check 1; D-Nat2 asks for "each green on its own base", so this is by design. Wording fixes:
(1) say that on a linear first-parent history the two bases are always ancestry-comparable and "incomparable" can only occur
with merge-heavy default histories, so expect few such exclusions; (2) say explicitly that `I_AB == I_BA` is checked on the
tree **and** that attribution runs on `I_AB` only.

## N5 — can outcome knowledge reach selection? (non-blocking)

No path from checker or detector output to selection exists in the design: selection uses timestamps, Python-touch and a
hash; anchors, bases and contamination come from the graph; no replacement; one round; the detector runs after labels from a
pre-frozen file map. Disclose three weaker channels in the policy:

1. **Candidate repositories were chosen using S17 outcomes** (the table cites "S17 eligible tests" and "existing ambiguous
   checker identities"). That raises oracle eligibility and cannot favour positives, but it is a prior-outcome selection.
   Say so, and that S17b is development evidence and never feeds S18.
2. **"Reject an unsuitable whole candidate in a preregistration revision" after dependency inspection** must be dated before
   the first pair ledger exists; afterwards a repository could be dropped because its pair list looked poor. Add: no
   repository changes after checkpoint (1).
3. **Detector revision "designated at freeze":** record the designation and its commit in the freeze file before any label;
   a later change is a new round.

## N6 — what the survivors are (non-blocking, must be in the report)

Final heads postdate the overlap. Survivors skew toward (a) later PRs never updated after the earlier merge (abandoned or
repositories without an up-to-date rule), because up-to-date later PRs contain `C` and fall out under B2, and (b) pairs where
the earlier PR was merged (closed-unmerged earlier ends cannot anchor). A conflict that a later author already repaired
(adapting to A without merging it) appears as a *control*. Hence: yield and positive rate are not prevalence, controls mean
"integrate cleanly as final heads", and the stratum says nothing about conflicts caught before merge in real workflows. The
design says most of this; add (a)–(b) with the contamination-exclusion count per repository.

## Minor

- `gh api --paginate --slurp` needs a recent `gh`; pin and record the `gh` version with the API version.
- `merge_commit_sha` on closed-unmerged PRs is a test-merge commit, never an anchor; the design is right to treat it as
  unresolved, say it so a mock test covers it.
- The detector runs on synthetic `L, A_L, B_L` commits; confirm crosswire accepts raw SHAs as refs in combined mode (it
  accepted `ref~0` and `refs/heads/…` in my T21 replay) and that the synthetic commits are reachable through a local evidence ref.
- Draft PRs: confirm "drafts included" also covers PRs that were drafts at close.

## Not verified

No GitHub behaviour (merge-commit semantics per method, `updated_at` consistency, list ordering, `gh` flags) was tested; the
local experiment used a synthetic repository with `git cherry-pick` standing in for GitHub's rebase merge, which preserves
author dates as GitHub does (*unverified on GitHub itself*). No pair of real PRs was examined.

## What I checked and found correct

- **Hash vectors.** I recomputed all three: `s17b-v1|123456789|4|5` → `91fbad73…6df4`, `s17b-v1|1|1|2` → `b6da358d…ce10`, `s17b-v1|1|2|3` → `20ac85bf…3322`. They match the table byte for byte. Encoding rules, tie-break, "changing the seed is a new preregistration" and the negative tests are present.
- **N1 as decided.** The text, the exclusion-stage table and the stop rule agree: metadata failures record rank, first failed filter and outcome but consume no slot; every post-metadata exclusion (head, anchor, contamination, base, integration, oracle, detector) consumes one with no replacement; the unevaluated tail is reported as unattempted, not as controls. "Equals eager filter-then-take-20" is true because all metadata filters depend only on the PR data and the order depends only on `(repo-id, A, B)`. The list-derived pre-ordering stage is limited to *provable* non-overlap, which is the safe direction.
- **B1 rule.** Operational and testable: n=1 method-neutral (`squash-n1`); n≥2 *rebase proven* needs the complete ordered sequence by full tuple or by `patch-id --stable`, never a mix; *squash proven* needs `C` single-parent, no match in the last-`n` chain by either key, `git cherry` all `+`, and an exact `B_PR..H_E` range check; anything else is `unresolved`; the inclusive last-`n` retrieval (`rev-list --first-parent --max-count=n C`) is stated; commit-message conventions are explicitly not evidence; closed-unmerged `merge_commit_sha` never anchors; `anchor_method` is recorded per pair. The test list covers n=1 both ways, n=3 squash, n=3 rebase by either proof, the conflict-resolved case, partial matches, a squash that copies a subject, an off-chain `C`, and a test-merge SHA.
- **B2 rule.** Three checks, all before integration and independent of checker output: (1) neither `C` nor `H_E` is an ancestor of `H_F`, plus the identical/ancestral-head rejection; (2) `merge-base(H_A, H_B)` must be in the default ancestry of `D`, multiple or missing bases unlabelled; (3) patch-id sets of `B_A..H_A` and `B_B..H_B` disjoint, unobtainable identity unlabelled rather than empty. Each failure consumes its slot and is counted per repository. Three positives and the negative are on the test list, and the design is honest that independently authored identical patches are excluded.
- **N2–N6** are adopted as I proposed, with the open-listing hole disclosed instead of closed (accepted; it is a stated coverage limit, not a hidden one).

## R1 — the ceiling cannot fill the slots, and the table-order traversal decides who starves (fix before checkpoint 1)

Arithmetic with the design's own request list. A pair evaluated in rank order needs detail (2 PRs), files (≥1 page each) and timeline (≥1 page each): up to 6 GETs, fewer when PRs are reused (cache). If a pair passes the metadata filters with probability *p* (both PRs Python-touching, unreopened, timestamps valid; I assume p ≈ 0.3–0.6 for these small libraries, *unmeasured*), a slot costs about 1/*p* pairs, i.e. roughly 10–20 GETs. After a pair earns a slot, both PR commit lists plus the anchor commit add about 3 GETs. So one repository costs about 20 × (10…20 + 3) ≈ 260–460 GETs, and eight cost **2,000–3,700 against a 1,500 ceiling**. Because traversal is fixed in table order, a ceiling that hits would leave itsdangerous and blinker (the last rows) with nothing, which the report would then describe as "unattempted" although the cause is budget allocation rather than sparse data.
Fix: pre-register per-repository GET sub-budgets (for example `floor((1500 − list/probe reserve) / 8)` each, with unspent budget *not* rolled forward in a data-dependent way, or rolled forward by a rule fixed in advance), and state that a repository stopping at its sub-budget reports its evaluated prefix. Alternatively raise the ceiling with a stated reason. Either choice is outcome-blind; what matters is that it is chosen before any ledger exists.

## R2 — the metadata filter order is not pinned (fix before checkpoint 1)

The ledger records the *first failed filter* at each rank, and each filter costs different GETs (detail is cheap; files and timeline are paginated). Without a fixed order, the recorded reason and the GET count depend on implementation order, and two correct implementations produce different ledgers and different prefixes at the ceiling. Pin it, cheapest and most-rejecting first, for example: list-derived overlap → PR detail (merged/closed consistency, base ref, timestamps, `changed_files`) → timeline (reopened) → files (Python touch, completeness against `changed_files`). Record which PR of the pair failed first (A before B).

## R3 — `git cherry` and PR commits that are merges (fix before checkpoint 1)

`git cherry` omits merge commits, so for a PR that merged the default branch into itself the output has fewer lines than the PR's commit count. I verified this locally on a squashed PR with commits `p1`, `merge main`, `p2`: the PR range holds 3 commits, `git cherry main pr <base>` prints 2 `+` lines. The rule "`+` for every PR commit" is therefore unsatisfiable (a silent `unresolved`) or, depending on the implementation, may be tested only against the non-merge lines. State it exactly: require `+` for **every non-merge** PR commit and the number of lines equal to the non-merge count; merge commits in the PR are covered by the "no tuple match in the last-`n` chain" condition. Add a test with a PR containing a default-branch merge, squash-merged (expected `squash-proven`) and rebase-merged (expected `unresolved`, because the rebase drops the merge and the chain of `n` commits cannot match one-to-one).

## R4 — order of the sequence comparison, and a cheap corroboration for the squash proof (fix before checkpoint 1)

(a) "match the complete PR list one-to-one, in order": say which order. `rev-list --first-parent` returns newest first, the PR commit list endpoint returns oldest first (*unverified*); compare after normalising to a stated direction and add a test with a reversed sequence that must **not** match.
(b) *Squash proven* is a negative proof: it holds if nothing matches, so a rebase merge whose commits were all rewritten (a merge queue, a bot, an author-rewriting policy) would be classified as squash with `D = C^`, which puts `n−1` of the PR's own commits inside `D` and makes `B_E` collapse. Add an outcome-blind corroboration: the set of paths changed by `C^..C` (with renames) must equal the PR files list's path set. Mismatch → `unresolved`. This is consistent with the design's decision not to require tree equality (it compares paths, not content, so conflict resolution still passes).

## R5 — small items (fix with the others)

- **Terminal-time ties.** The tie rule is "accept only an unambiguous earliest integration on that chain": say what happens when one PR is merged and the other closed at the same instant (the merged one is `E`) and when both are merged at the same timestamp (order on the first-parent chain decides; if `C_E` and `C_F` are the same commit, unresolved).
- **"Earlier PR is merged" is metadata.** It is known from list data, so a closed-unmerged earlier PR could be a non-consuming metadata filter rather than burning a slot as `unresolved`. The present rule is conservative and acceptable; choose explicitly, before checkpoint (1), whether such pairs are in the cohort (consume) or out of it (filter), and report the count either way. It does not affect the validity of anything else.
- **Per-repository exclusion counts.** The N6 disclosure promises contamination and anchor counts per repository; list `anchor_method` counts in the same table so the survivor-bias statement can be checked.

Local experiments used synthetic repositories only. I did not read the unchanged parts of the design for new text beyond a full read of revision 3.

## Verdict on authorizing checkpoint (1): **NOT YET. Three small code/policy fixes (C1–C3), then yes.**

The implementation follows the approved design closely and, importantly, **nothing in it can make an API call or a fetch before checkpoint (1) and a matching authorization** (below). The three conditions are things that would be expensive or impossible to repair after the checkpoint: the code hash is pinned in it, the round is one-shot, and a wrong assumption would be discovered only during collection.

| C1 | **major (condition)** | Timeline terminal-event equality is an unverified GitHub assumption; if wrong, every merged PR fails the metadata filter and the round yields nothing |
| C2 | **major (condition)** | The GET allowlist is `startswith('repos/')`: any repository and `repos/../user` pass |

## Does the code do what the policy says? — verified item by item

- **Seeded hash order.** `pair_hash` reproduces the three frozen vectors (`91fbad73…`, `b6da358d…`, `20ac85bf…`); noncanonical numbers (`01`, `1 `, ` 1`, `+1`, `1.0`, `True`) are rejected; `A<B` enforced; sort key `(hash, A, B)` with numeric tie-break; rank independent of input order (tested).
- **Overlap.** Strict `max(created) < min(end)`, equality is not overlap; list-derived uncertain pairs are kept as candidates and rejected at metadata; only *provable* non-overlap leaves the order; recheck against detail intervals (`detail-overlap-inconsistent`, no slot).
- **Lazy walk and 20-pair cap.** `select_pairs` walks the hash order, evaluates A fully (detail → timeline → files) before B (R2, short-circuit proven by test and by reading `Metadata.load`), consumes a slot only for a pair that passes, stops at 20 (`reason='cap'`), records rank, first failed PR/stage/filter for every evaluated pair, reports the unattempted tail, PR reuse and per-PR counts. Metadata failures never consume a slot; every post-metadata outcome keeps it (`prepare_pair` returns `unlabelled` or `unattempted`, never a replacement).
- **R1 budgets.** `per_repository_get_budget=187` and `global_get_headroom=4` give exactly 1,500; the budget is counted per `repos/<owner>/<repo>/` prefix from the durable request log (survives restarts), never rolled forward; a `RepositoryCeiling` continues to the next repository, a global `Ceiling` marks the rest unattempted. Requests are claimed with `O_EXCL` and `fsync` before running; a started request without a durable response is never retried.
- **GET only.** `gh api --method GET --include` with an explicit API version header; pagination follows only `https://api.github.com` links (untrusted host → incomplete); non-200, malformed body, timeout → `Incomplete`; `Retry-After` / `x-ratelimit-remaining: 0` stops before the next request. The code contains no `POST`/`PATCH`/field flags/`push`.
- **Pagination (N2).** One extra full tail page after the first sub-bound item, violation count, continue to exhaustion on any violation or on out-of-order `updated_at`; final Link and page count recorded; the coverage hole is stated in the output.
- **Anchors (B1, R3, R4).** `anchor()` implements: merged and `C` on the first-parent chain; count/list completeness; PR sequence oldest-first with `commits[-1]==head`; true merge `D=parents[0]` (second parent must be the head); `n==1` method-neutral; `n≥2` rebase proof by the whole ordered (author, email, date, subject) sequence or the whole patch-id sequence, `D=C~n`; squash proof only if no tuple/patch-id match, `git cherry C head base` returns `+` for **exactly the non-merge PR commits**, and the changed-path set of `C^..C` equals the PR file list including previous names; anything else `unresolved`. Reversed sequences never match (tested). Terminal ties follow the policy (one merged → that PR; both merged → first-parent order; same `C` or neither merged → unresolved); an earlier closed-unmerged PR consumes its slot as `unresolved` (the R5 choice).
- **Contamination (B2).** Before any integration: `C` or `H_E` ancestor of `H_F`; ancestral/identical heads; `merge-base(H_A,H_B)` unique and an ancestor of `D`; stable patch-id sets of `B_A..H_A` and `B_B..H_B` disjoint; unavailable proofs are `contamination-proof-unavailable`, never an empty set. Independent of checker output and commit messages.
- **Own bases / integration.** `own_bases` (unique merge-base, not contained, comparable ancestry, equality allowed); native `merge-tree --write-tree` merges, unique `merge-base(A_L,B_L)==L`, reverse-tree equality, evidence refs under `refs/s17b/`, all after the graph ledger.
- **M3.** `benchmarks/s17/m3.py` hashes to `f9c64ecb…e5b5` (pinned in the code and checked by `prepare`); `m3_contract` runs the frozen `delta` for each own base, then the frozen `label` on `(L, A_L, B_L, I_AB)`, then `minimal_attribution` on `I_AB` only, unlabelled if uncertain; no oracle is executed.
- **Checkpoint (1).** `prepare` refuses the template (cutoff/pins unset), a cutoff after "now", a changed M3, and any change to the protocol fields; it writes a `0600` file with `O_EXCL`, `fsync` of file and directory, the embedded policy and its canonical hash, and the hashes of all `s17b` code, tests, the design, M3 and `conformance/git.py`. I recomputed the 22 pins in `s17b-implementation.json`: all match. Tests: **76 passed**.

## Can anything call the API or fetch before checkpoint (1)? — No

Every network path begins with `Permit.verify()`: `GhGet.get` (before the `gh --version` check, before the cache, before any runner call), `ObjectStoreTransport.__call__`, `fetch_head` and `prepare_pair`. `verify` needs the checkpoint file, a separate authorization file bound to the checkpoint hash with `scope` and `approved_by`, and an unchanged code hash. Probes with a spy runner: no checkpoint → `FileNotFoundError`, **0 runner calls**; checkpoint but no authorization → `FileNotFoundError`, 0 calls; the unset template → `ValueError` (cannot form a checkpoint). Import performs no I/O; `python -m benchmarks.s17b` only writes a checkpoint (offline). `graph.py` contains no network operation.
Residuals, all procedural and already disclosed: the authorization is a JSON file (I forged one in a scratch directory and `verify` accepted it; there is no signature); runners and the transport are injectable; the clone is outside the code (C3).

## Conditions before checkpoint (1)

**C1 — timeline equality (`timeline_filter`).** A merged PR passes only if `max(created_at of 'merged' events) == merged_at` exactly (for closed-unmerged, the `closed` event against `closed_at`). If GitHub's timeline event time differs from the PR field by even one second (merge queue, API merges, rounding), every merged PR fails `lifecycle-terminal-unproven` with no slot consumed. The round is one-shot, the failure costs a timeline GET per PR from the 187-GET budget, and the pair universe silently collapses to closed-unmerged pairs, none of which can anchor. I could not verify the equality (no API access).
Fix: define the proof as "the terminal event exists and `|event − field| ≤ T`" with a stated T (60 s) or, better, "exists and is the last terminal event", and add an outcome-blind health stop: if the first 10 fully loaded merged PRs of a repository all fail this filter, stop that repository as `acquisition-incomplete` and report it instead of spending the budget.

**C2 — allowlist (`GhGet.get`).** The accepted endpoint test is `startswith(('repos/','rate_limit'))`. I confirmed `repos/some-other/unlisted-repo` and `repos/../user` are issued, and the budget logic then charges them to an arbitrary prefix. Restrict to a pattern built from `policy['repositories']` (`repos/<listed>/(pulls|issues|commits)...`), reject `..`, empty segments, and `%` encodings, and allow `rate_limit` only if it is ever used (nothing calls it; remove it, together with the 4-request headroom or document its use).

**C3 — the clone.** Heads are fetched into "a disposable temporary clone", but nothing creates it, fetches the default-branch history, or accounts for those bytes; the README says "the caller can wire … local disposable graphs". That step is the largest transfer, it runs after authorization, and it is the only network operation outside `Permit` and the 2 GiB accounting. Implement it in the same module under the same gates (a `prepare_clone` that uses `ObjectStoreTransport` for the initial fetch of the pinned default branch, records the fetched default SHA against the one pinned by `collect_metadata`, and counts toward `GitBudget`), or state in the authorization exactly which command the caller will run and that its bytes are counted by hand. Also pass `-c gc.auto=0 -c maintenance.auto=false` to every fetch: an automatic repack can shrink the object store and `after<before` is treated as *unmeasurable*, which would stop the whole cohort for a harmless reason.

## M1 — wasted GETs on out-of-window PRs (should fix with C1–C3)

`list_closed` keeps every PR it reads, including the tail page (up to 100 PRs updated before 2022), and `enumerate_pairs` ranks all of them; the window is then a *lazy* filter that costs one detail GET per failing PR per evaluation. For a small repository the tail page can be most of the universe. Terminal time is in the list item, so "provably outside `[2022-01-01, cutoff)`" is known before ranking and, like provable non-overlap, cannot change the relative hash order of the remaining pairs or consume a slot. Excluding them from the pair universe (and counting them in `list_counts`) selects the same set and spends fewer of the 187 GETs. It needs one sentence in the design table ("before ordering: provable non-overlap **or** provable terminal-window failure").

## Minor

- **m1 Over-exclusion, empty default commits.** A squash with an *empty* commit among the previous `n−1` default commits is `patch-proof-unavailable` (reproduced): the code asks for a patch-id of every commit in the last-`n` chain, but an empty, root or merge commit that is not a PR commit cannot match any PR patch. Compute patch-ids only for the PR commits and compare them against non-empty chain commits; treat the others as non-matching.
- **m2 Over-exclusion, merge from default.** Any PR whose range contains a merge of the default branch fails contamination test 3 with `contamination-proof-unavailable` (reproduced); this is the policy as written ("merges … unresolved"), but squash anchoring was deliberately made tolerant of such PRs (R3), so most pairs of branches that merged `main` will be lost one stage later. State the expected yield effect in the report, or define patch sets over the non-merge commits of the range (the content a merge brings in from default is already in `D`).
- **m3 Dead parameter.** `anchor(..., source_base)` is never used; `prepare_pair` computes `source_bases` from `parents(commits[0])` but nothing compares it with the range base. Either compare them or drop it.
- **m4 Re-fetch for reused PRs.** `prepare_pair` fetches both heads for every pair even when the PR was fetched for another pair; the object store does not grow but the network round trip and receipt repeat. Cache per PR number (the policy says "deduplicate retrieval").
- **m5 List duplicates.** A PR that appears on two pages with *different* content (it was updated meanwhile) raises `Incomplete('PR moved/changed')` for the whole repository; the design only asks to track duplicates. Keep the later record (highest `updated_at`), log the move, and fail only on contradictory terminal data.
- **m6 Checkpoint hygiene.** The policy template says `status: implementation for review only; collection not authorized`; `prepare` does not require it to change, so a checkpoint could embed that text. Require a status change. Also pin the Python version and the Git version (they affect `fromisoformat`, `merge-tree --write-tree` requires Git ≥ 2.38) in checkpoint (1), not only at (2). `GitBudget` and the measurement ceiling (`maximum_measurement_seconds`, 5,400) are policy values but not enforced anywhere in this package; checkpoint (2) and the measurement orchestrator remain to be written, as the README says.
- **m7 Mislabel.** `native_merge` labels any `merge-tree` non-zero exit (including exit 128 for corruption) as `textual-conflict`; exit 1 is the conflict code.

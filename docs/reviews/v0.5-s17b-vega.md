## B1 — squash versus rebase: a single-parent commit cannot prove "squash", and the design gives no other evidence (blocking)

**Design text.** "When `merge_commit_sha` identifies its single-parent squash integration commit … `D = that commit's parent`";
"a single-parent commit alone does not distinguish squash from the last commit of a rebase merge; ambiguous merge-method
evidence remains unresolved"; the test list asks for "ambiguous merge-method evidence". Nowhere is the evidence defined.
An implementer has two choices: treat every single-parent commit as a squash (wrong for rebase merges) or treat every one
as ambiguous (the squash branch never fires). Neither can be tested.

**What the graph shows** (local experiment, scratch repo; PR of 3 commits, default branch advanced meanwhile):

```
squash : 03a6199 p=c932da5 (1 new commit, author date = squash time, subject "squash (#1)")
rebase : dc5eafe p=d0ab81a / d0ab81a p=cfe547e / cfe547e p=c932da5   (3 commits, author dates 01-03, 01-02, 01-01 preserved)
patch-id of the 3 PR commits:      921527f986c7  d532f052b535  151d0d05f0aa
patch-id of the last 3 on rebase:  921527f986c7  d532f052b535  151d0d05f0aa      (identical)
patch-id of the squash commit:     7c6524512ca8                                (matches none)
git cherry <squash> <pr>  → + + +        git cherry <rebase> <pr> → - - -
```

So for a PR with `n` commits (`commits` in the PR detail), a rebase merge leaves `n` consecutive first-parent commits
ending at `C = merge_commit_sha`, preserving author, author date and subject and (unless conflicts were resolved)
patch-ids; a squash leaves one commit that matches none of them. Consequences:

1. **`n == 1`: squash and rebase are indistinguishable by graph and equivalent for the anchor** — `C^` is the correct
   pre-PR default state either way. State this as the rule: n=1 needs no merge-method evidence.
2. **`n ≥ 2`:** classify from the PR commits, not from `C` alone:
   - *rebase proven* if the last `n` first-parent commits ending at `C` equal the PR commits one-to-one by (author, author date, subject) **or** by `git patch-id --stable`;
   - *squash proven* if `C` is single-parent, **no** commit in `C~(n-1)..C` matches any PR commit by those keys, and `git cherry C pr-range` reports `+` for every PR commit;
   - anything else (partial matches, conflict-resolved rebases whose patch-ids changed) → `default-anchor-unresolved`.
3. **Rebase merges need not be thrown away.** With the match in 2, `D = C~n` (the parent of the first rebased commit) is exactly as provable as the squash anchor. Keeping them unresolved is acceptable for a first round (it lowers yield), but then say so and make the classification above the *only* thing that separates "unresolved" from "squash": a classification that can fail is the point.
4. **Do not rely on commit-message conventions** (`(#N)`, "Squashed commit of …"): they are configurable and typed by humans. (*Unverified:* GitHub's default squash message carries the PR number; the design should not depend on it either way.)
5. Add tests (all synthetic, as the design already plans): n=1 squash and n=1 rebase both accepted with the same `D`; n=3 squash accepted; n=3 rebase → unresolved (or accepted with `D=C~3` if item 3 is adopted); n=3 rebase with a conflict-resolved commit (patch-id changed, author/date/subject preserved) → the key rule must still classify it, or leave it unresolved, never squash; a "squash" whose message copies a PR commit subject must not be called a rebase; `C` off the first-parent chain → unresolved.

Also record, per pair, which rule fired (`anchor_method ∈ {merge, squash-n1, squash-proven, rebase-proven, unresolved}`) so a reviewer can audit the 10% sample.

## B2 — head contamination has no procedure (blocking)

**Design text.** "Reject identical/ancestral heads and cross-contamination … Require graph evidence; unresolved
squash/cherry-pick equivalence is unlabelled." This is the check that keeps the two-branch experiment honest, and it
names no operation. Three concrete holes:

1. **Later PR contains the earlier PR's integration.** If B was updated from the default branch after A merged, `C` (A's
   integration) is an ancestor of `H_B`, and `B_B = D`/later than `D`. The design never states the test `C ∉ ancestors(H_B)`.
   For a true merge `C`, `H_A ∈ ancestors(H_B)` is the equivalent; for a rebase merge it is `C` (the last rebased commit).
   This matters most: B is the **later-ending** PR, and many repositories require branches to be up to date before merge,
   so *merged* later PRs are the ones most likely to contain A.
2. **Stacked PRs / shared PR-only history.** `H_A` and `H_B` can share commits that are on neither default branch nor the
   bases (B branched off A's branch; A later force-pushed, so `H_A` is not an ancestor of `H_B`). Test:
   `merge-base(H_A, H_B)` must be an ancestor of `D` (on default); equivalently `rev-list H_A H_B ^D` has empty intersection
   of `rev-list H_A ^D` and `rev-list H_B ^D`.
3. **Cherry-picked or rebased copies.** Content of A already inside B without ancestry. Test: the `git patch-id --stable`
   sets of `B_A..H_A` and `B_B..H_B` must be disjoint; a non-empty intersection → `contaminated-heads`, unlabelled.

Also state that the contamination test runs **before** the integration, uses only graph/patch-id evidence, and is
independent of any checker output (so it cannot be tuned after seeing results). Add the three cases to the synthetic-graph
test list, plus the negative (two unrelated PRs with equal-looking changes are not flagged by patch-id).

## N1 — evaluation order, the request ceiling and exclusion stages (non-blocking, must be settled before freeze)

- **Ceiling.** Requests needed per candidate PR: list pages (shared), 1 detail, ≥1 `files` page, ≥1 `timeline` page, plus
  1 commit detail per anchor. Evaluating *every* PR of every overlapping pair "after the fixed filters" then sorting is
  hundreds of PRs per repository; 1,500 GETs across 8 repositories cannot cover it. If the ceiling hits mid-way, the
  candidate ledger — and therefore the hash-ordered top 20 — depends on fetch order, which breaks the "reviewer can reproduce
  the cap" promise.
- **Fix (keeps the selection rule unchanged):** enumerate overlapping pairs from list data only (created/closed/merged
  timestamps), order them by the hash, and **walk that order**, evaluating the metadata filters (detail, files, timeline)
  lazily until 20 pairs pass or the order is exhausted. This selects exactly the same set as eager evaluation (the filters
  are metadata, the order depends only on `(repo-id, A, B)`), costs about `2.2 × 20` PRs per repository, and makes the
  ceiling a statement about a deterministic prefix. Record the rank of every evaluated pair and every filter outcome.
  Rough fit: 8 × ~45 PRs × 3 GETs ≈ 1,100 plus list pages and anchor lookups — inside 1,500 only with lazy evaluation.
- **Exclusion stages are inconsistent.** One paragraph removes pairs with "missing/inconsistent timestamps" from the
  cohort *before* ordering (they do not consume the cap); another keeps "incomplete lifecycle evidence", "reopened" and
  "metadata-uncertain" as *selected-but-unlabelled* (they do consume it). Both are outcome-blind, but the report's
  arithmetic needs one table: for each exclusion, the stage (before ordering / after ordering), whether it consumes a slot,
  and which data it needs. With lazy evaluation, the natural rule is: only the list-derived overlap is pre-ordering;
  everything else is evaluated in order and consumes the slot.
- **Python-touch from list data is not possible** (list items carry no file counts): confirms the lazy approach.

## N2 — timestamp pagination stop rule (non-blocking)

The rule is directionally valid: if every closed PR satisfies `updated_at ≥ end_i`, a descending-`updated` list can stop at
the first PR with `updated_at < 2022-01-01` (a whole page is not needed, but is harmless). Moving items cannot be skipped:
`updated_at` only grows, so a concurrent update moves a PR to the front and the only effect is a duplicate. Gaps:

1. **The tail is never validated.** The check `updated_at ≥ end_i` runs only on the PRs retrieved; PRs beyond the stop
   point cannot be tested. (*Unverified:* imported or mass-edited repositories may violate it; I did not query any.)
   Mitigation: after the first sub-bound item, read at least one further full page and record the number of violations
   (`end_i ≥ bound` among items with `updated_at < bound`); any violation → continue to the end or declare incomplete.
2. **Reopened PRs currently open are absent** from `state=closed`. A PR closed inside the window and reopened later (still
   open at collection) never enters the universe and is not counted as an exclusion. Count them with a second listing
   (`state=open`, filtering `created_at < cutoff`) or state the hole in the limitations.
3. **Cutoff drift.** `collection_cutoff` is fixed, collection happens later; a PR closed before the cutoff but reopened and
   re-closed after it carries a post-cutoff `end_i` and is dropped (state it). Set the cutoff ≤ collection start so this is
   the only drift.
4. Record the final page's `Link` header and total pages per repository, so "complete" is checkable.

## N3 — seeded hash-order contract (non-blocking)

The contract is exact enough: numeric repository ID, canonical decimals, `A < B`, UTF-8, literal `|`, no newline, digest
bytes ascending, numeric tie-break. Confirmed properties: order-independent of input, stable across repository renames,
no dependence on outcomes. Add to the policy:

- **Test vectors** (SHA-256 of the exact bytes): `s17b-v1|123456789|4|5` →
  `91fbad73416315bd6360c6a6a91935eff18dc9fbdcc0570f30f2405f63486df4`;
  `s17b-v1|1|1|2` → `b6da358de0571c50d09606c27f6035a34683751287fe297c8aa2c5baf074ce10`;
  `s17b-v1|1|2|3` → `20ac85bfa6ed7b2292f5327fce2f207647775a8a0957053997bf6d7a52293322`.
  Include a "leading zero / extra whitespace / uppercase hex" negative test.
- State that the seed string is public and fixed and that **changing it is a new preregistration**, not a retry.
- **PR reuse.** Hashing over *pairs* weights a long-lived PR by how many partners it has (a PR open for a year appears in
  many pairs). Report the number of distinct PRs, the maximum pair count per PR, and the cluster-level effect; consider a
  deterministic cap on pairs per PR (hash order keeps it outcome-blind) only if the ledger shows heavy reuse — never decide
  after seeing labels.

## N4 — M3 reuse: both checks sufficient, small over-exclusion (non-blocking)

Sufficiency argument:

- Check 1 (`delta(B_i → H_i)` empty) is the "green on its own base" condition of D-Nat2. When `B_i == L` it duplicates the
  M3 tip condition for that PR; when `B_i < L` it is a distinct check and is required.
- Check 2 (frozen `label(L, {A_L, B_L}, I)`) rejects errors from normalising a head onto `L` (default drift ∩ PR change)
  and then defines positives as errors absent from both normalised tips. Together they cover: PR-red-on-own-base, red-after-
  normalisation, and new-in-integration.
- Leave-one-out minimal attribution uses `A_L`/`B_L` as the one-branch states, which are exactly the states the label
  compares against; consistent.

Over-exclusion (acceptable, document it): a PR red on its own base but green after normalisation onto `L` (the fix arrived
in default drift) is excluded by check 1; D-Nat2 asks for "each green on its own base", so this is by design. Wording fixes:
(1) say that on a linear first-parent history the two bases are always ancestry-comparable and "incomparable" can only occur
with merge-heavy default histories, so expect few such exclusions; (2) say explicitly that `I_AB == I_BA` is checked on the
tree **and** that attribution runs on `I_AB` only.

## N5 — can outcome knowledge reach selection? (non-blocking)

No path from checker or detector output to selection exists in the design: selection uses timestamps, Python-touch and a
hash; anchors, bases and contamination come from the graph; no replacement; one round; the detector runs after labels from a
pre-frozen file map. Disclose three weaker channels in the policy:

1. **Candidate repositories were chosen using S17 outcomes** (the table cites "S17 eligible tests" and "existing ambiguous
   checker identities"). That raises oracle eligibility and cannot favour positives, but it is a prior-outcome selection.
   Say so, and that S17b is development evidence and never feeds S18.
2. **"Reject an unsuitable whole candidate in a preregistration revision" after dependency inspection** must be dated before
   the first pair ledger exists; afterwards a repository could be dropped because its pair list looked poor. Add: no
   repository changes after checkpoint (1).
3. **Detector revision "designated at freeze":** record the designation and its commit in the freeze file before any label;
   a later change is a new round.

## N6 — what the survivors are (non-blocking, must be in the report)

Final heads postdate the overlap. Survivors skew toward (a) later PRs never updated after the earlier merge (abandoned or
repositories without an up-to-date rule), because up-to-date later PRs contain `C` and fall out under B2, and (b) pairs where
the earlier PR was merged (closed-unmerged earlier ends cannot anchor). A conflict that a later author already repaired
(adapting to A without merging it) appears as a *control*. Hence: yield and positive rate are not prevalence, controls mean
"integrate cleanly as final heads", and the stratum says nothing about conflicts caught before merge in real workflows. The
design says most of this; add (a)–(b) with the contamination-exclusion count per repository.

## Minor

- `gh api --paginate --slurp` needs a recent `gh`; pin and record the `gh` version with the API version.
- `merge_commit_sha` on closed-unmerged PRs is a test-merge commit, never an anchor; the design is right to treat it as
  unresolved, say it so a mock test covers it.
- The detector runs on synthetic `L, A_L, B_L` commits; confirm crosswire accepts raw SHAs as refs in combined mode (it
  accepted `ref~0` and `refs/heads/…` in my T21 replay) and that the synthetic commits are reachable through a local evidence ref.
- Draft PRs: confirm "drafts included" also covers PRs that were drafts at close.

## Not verified

No GitHub behaviour (merge-commit semantics per method, `updated_at` consistency, list ordering, `gh` flags) was tested; the
local experiment used a synthetic repository with `git cherry-pick` standing in for GitHub's rebase merge, which preserves
author dates as GitHub does (*unverified on GitHub itself*). No pair of real PRs was examined.

## B1 — complement leak through `attribution_accuracy` (blocking)

`suppress_small_cells` decides "small" from the fields in `COUNT_FIELDS` only. The attribution cell exposes `attribution_accuracy` (a fraction) and `attribution_labelled` (a count ≥ 5) but **not** the number of wrong attributions, which is `labelled × (1 − accuracy)`. When that number is 1–4 it is a small outcome count that nothing hides.

Probe (public function, unchanged code):

```
micro: tp=60 fp=0 fn=0, attribution_labelled=60, attribution_accuracy=58/60
suppress_small_cells(...)  →  micro NOT suppressed; visible accuracy 0.96667, labelled 60
derived wrong attributions = 2
per-rule CW001: labelled 20, accuracy 0.95  →  1 wrong attribution, visible
control: any visible small fp (e.g. 2) suppresses all four statistical blocks (works as designed)
```

The preregistration promises "any small count anywhere in the linked statistical table suppresses all linked blocks" and "hide … derived shares, ratios". The complement is the inverse (labelled − correct) of a published ratio, i.e. exactly the case that policy exists for. Because the attempt is irreversible, fix it before authorization:

- Treat the derived counts as primary cells: compute `wrong = labelled − round(accuracy × labelled)` (or better, have the export carry integer `attribution_correct`/`attribution_incorrect` internally and drop the ratio from the public view when either is 1–4) and include them in the "any small count" test, for the micro cell and for each rule cell.
- Audit every other published ratio for the same property. I checked: `precision`/`recall` (numerators and denominators `tp`, `fp`, `fn` are fields — covered), `unlabelled_share` (`unlabelled_cases` is a field), `unlabelled_prediction_share` (`unlabelled_predictions` is a field), Wilson intervals (functions of covered counts), `repositories`/`replicates`/`seed` (fixed metadata). Attribution is the only uncovered ratio.
- Add a test with `58/60` and `19/20`; the current suite has no attribution case (`rows(...)` uses empty `attribution` lists).
- Regenerate `holdout-v2-apparatus.sha256`, `successor_seal_sha256`, `after` in the amendment, and the tests/supporting pins, then I re-audit the diff.

## D1 — suppression versus the gates: the expected good outcomes cannot be published (decision for Polaris)

With the expected 60 positives, the precision gate can pass only for `fp ∈ {0, 1}` (probe above; with `fp=1` needs `tp ≥ 52`, with `fp=2` needs `tp ≥ 67`, impossible here), and recall passes for `fn ≤ 12`. The suppression rule hides **every statistical block** when any count is 1–4. Consequently:

| Outcome (60 positives) | Public result |
|---|---|
| `fp=0, fn=0` | gates and numbers published |
| `fp=1` (precision still a pass) | **everything suppressed**; no public gate-pass claim |
| `fn` in 1–4 (recall still a pass) | **everything suppressed** |
| `fn` in 5–12 with `fp=0` | published |
| `fp ≥ 5` | published as a fail |

So a result that passes both gates with one false positive, or with three misses, exists only in the private journal and the audit; the public aggregate says "suppressed" with status `complete`. The preregistration states "a suppressed result makes no public gate-pass claim", so the design is internally consistent, but I doubt it is intended: the policy was written for small *rare-event* cells, and here the pass region of the pre-registered gate lies inside the suppression region. Polaris should choose and pre-register one of:

1. **Accept it** and say in the preregistration that the likely good outcomes publish as "suppressed", with the audit as the only evidence (honest, but the public gets nothing).
2. **Publish the categorical gate verdicts and attempt status outside the suppressed blocks** (`provisional pass` / `fail` / `insufficient data` per micro gate), keeping counts and ratios suppressed. A verdict reveals only a range (e.g. precision pass ⇒ `fp ≤ 1`), not an individual count; state that explicitly.
3. **Lower the minimum cell size for this aggregate-only synthetic stratum** (v2 is constructed, not natural data), with a reason.

I recommend 2. Whatever is chosen must be written before the attempt (it is a publication rule, not a gate), and Deneb's tests should pin it.

## M3 — the measurement environment is neither pinned nor recorded (major)

The attempt marker binds `manifest`, `source`, `eval` and `seal` hashes. It does not record the detector interpreter (`--detector-python`: version and path), the Git binary version, the OS, or the process environment. The sealed `measure.evaluate` runs the detector with `os.environ | {'PYTHONPATH': source, 'GIT_OPTIONAL_LOCKS': '0'}`, so locale, `PYTHONHASHSEED` and any `PYTHON*`/`GIT_*` variables are inherited. Python's `ast` and Git's merge behaviour vary by version; this is the S17 "controller provenance recorded only post-run" limitation again. Before authorization: add a private `measurement-environment.json` written at claim time (interpreter `sys.version`, Git version, `uname`, sorted environment keys, locale) — **not** into the compared metadata, or report-only on another host would refuse — and have the authorization name the detector interpreter and Git version. My T21 replay found no dependence on four `PYTHONHASHSEED` values (it ran under `LC_ALL=C` only, so locale was not varied), which is not a guarantee for 240 constructed cases.

## Minor

- **m1 Stale `.next` wedge.** `_write_private(..., replace=True)` creates `<name>.next` with `O_EXCL`. A crash between that create and `os.replace` leaves it; the next replace of the same file raises `FileExistsError` (reproduced). For `measurement-rows.json` and the output file that blocks report-only until someone deletes the temp by hand. Unlink a stale `.next` (never the marker) before creating.
- **m2 Stray file wedge.** `AttemptJournal.read` raises `Unknown journal record` for any extra file in the journal directory (reproduced with `.DS_Store`). Fail-closed is intended, but on macOS this is easy to trigger; ignore dot-files or document it.
- **m3 Misleading message.** If the first attempt completes but the `--output` file already exists, `_write_private` raises and `main` prints "attempt unavailable or interrupted" although the journal is complete (report-only recovers it). Distinguish "export failed" from "attempt interrupted".
- **m4 Complete-but-unmarked journal.** A kill between the last `result` and `state('complete')` yields all rows but state `running`, so the export is `interrupted` with gates `insufficient data`. Conservative and intentional (the source/apparatus re-check had not run); say so in the preregistration so nobody reads it as data loss. The rows remain in the private journal for the audit.
- **m5 No tamper evidence on journal rows.** Rows are not hash-chained (`result` records bind the case identity, not the row). Isolation is procedural already; a cheap improvement is to write `sha256(row)` into the following `started` record and the sha256 of all rows into `measurement-state.json` on completion.
- **m6 Unlabelled-prediction share is vacuous by construction.** `evaluate` returns early for ineligible cases and `seal.py` puts them under `excluded`, outside `sealed['cases']`, so the exclusion block and `unlabelled_*` shares are 0 except for out-of-scope findings inside eligible cases. State that in the preregistration (it is the v0.4 M2 point again) so the 0 is not read as evidence of low noise on excluded cases.

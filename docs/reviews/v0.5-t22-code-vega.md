## Findings by review focus

### 1. Can batching change an output byte, an error text or an error order?

I found none. What I checked and why it holds:

- **Order and lazy replay.** `_PairMerges.requests` is `itertools.combinations(commits, 2)` over the same SHA order as the engine's `itertools.combinations(zip(branches, shas), 2)` loop (SHAs are distinct, enforced earlier), so the i-th request is the i-th pair. Results are consumed with an explicit `pair == (a, b)` check; any mismatch disables batching and clears the queue, so a changed traversal cannot receive another pair's result. The first chunk is requested inside the first `conflicts()` call, i.e. after that pair's summaries, so the stderr warning order of `get_summary` is unchanged (also pinned by `test_merge_error_follows_that_pairs_summaries`, which passes against the serial source).
- **Chunk failure.** `_merge_records` accepts a chunk only if the exit code is 0, stderr is empty, there are exactly `count` records, each with status `0`/`1`, a hexadecimal non-null tree of the right length, no paths on a clean record, and nothing left over. Any deviation makes every pair of the chunk `None`, and each `None` pair is answered by the original serial `merge_tree_conflicts` **at the position where the serial program would have called it**, so the error text and the point of failure are the serial ones. E4 (unrelated root inside a chunk, missing blob, read-only objects) gave identical results and identical `GitError` text in all pairs.
- **Speculative stderr.** `_try_git` captures stderr and never prints; its failures are swallowed into "not trusted". A user's `GIT_TRACE=2` makes stderr non-empty, which silently selects the scalar path (identical results in E4).
- **Capability probe and guard.** `_capable` is evaluated once per `_PairMerges`, only for ≥3 branches. The guard `git config --null --get-regexp` for `merge.*.driver`, `filter.*.{clean,smudge,process}`, `extensions.partialclone`, `remote.*.promisor` requires exit status 1 and empty output and stderr, so a configured driver, filter or promisor remote, or an unreadable configuration, disables speculation (E4: driver configured → batch disabled, results identical). `git config` follows includes and `-c`/environment configuration, so those are covered too. `merge-tree` runs no hooks. Everything else that influences merge results (`merge.renames`, `merge.conflictStyle`, attributes, renormalize, rename limits) is read identically by the batch and the scalar process.
- **Result equivalence.** E3: 1,205 + 66 + 6 pairs identical, including 274+ conflicted pairs, criss-cross virtual bases, orientation `(a, b)` kept, chunks beyond 256. Conflict paths go through the same `os.fsdecode` and `sorted(set(...))` as the scalar parse (the byte-name parity test covers this).
- **Boundary details I verified.** `len(a)` is used as the object-id length: correct for SHA-1 and SHA-256 (Altair's notes say SHA-256 was exercised). `status == b'1'` with any path is rejected. A conflicted record with no path (status `0`, empty list) is accepted and equals the scalar result `[]`.
- **Combined/plan** are untouched (the patch changes only the pairwise `analyze`), and `--no-textual` never builds `_PairMerges`.

### 2. The bounded ancestry index: is "unique best common ancestor" proven correctly?

**Yes.** The argument, which I checked line by line against `_build`:

1. `rev-list --topo-order --parents` lists every commit after all of its children. The code verifies completeness and order: every parent must be present and later in the listing, the tips must be present, ids must be well-formed, no duplicates, listing must end in a newline, row count and bytes are capped. A truncated, grafted-looking or inconsistent graph returns `{}`, and `{}` makes `unique()` return `None`, so the engine calls the scalar `git.merge_base` exactly as before.
2. Processing children first, each node's mask is the union of the tips that reach it. A node X with ≥2 tips in its mask is a common ancestor of every pair inside the mask; it is a **best** common ancestor of the pair iff no proper descendant is also common. If some proper descendant Y is common, X's child on the path to Y is an ancestor of Y and so also common; conversely a child whose mask contains the pair is a common proper descendant. So "no child mask ⊇ pair" is exactly the definition (the `mask in child_masks` shortcut is the special case in which one child covers every pair).
3. `best[pair] = None if pair in best else sha` keeps only pairs with exactly one best ancestor; ambiguous pairs and pairs without a common ancestor are absent, so they fall back to the scalar query. A unique best common ancestor equals what `git merge-base a b` prints, because scalar Git returns one best common ancestor.
4. When a tip is an ancestor of another tip it gets both bits, and the base is that tip, as in Git.

Empirical confirmation (E1, E2): 6,451 pairs over 200 random DAGs (≈ 1,267 + 5,184), **0 wrong** answers, 0 spurious fallbacks on unique pairs, 421 ambiguous pairs correctly returned `None`, 351 no-base pairs correctly `None`; under fully random timestamps (E2) scalar Git always agreed with the true best ancestor and with the index (1,546 pairs), so clock skew did not produce a base disagreement in anything I generated.

**Do the bounds fall back invisibly?** Every bound returns `{}` (tips outside 4–64, commits > 20,000, bytes > 4 MiB, capture > 1 s, construction > 1 s) or `None` from `_parent_graph` (any stderr output, non-zero exit, timeout, OS error); none can raise, none prints. The process is killed and both pipes are closed in `finally`, also on `KeyboardInterrupt`. The conditions that make a replaced or truncated history unsafe all disable the index: `GIT_GRAFT_FILE`, `GIT_SHALLOW_FILE`, `GIT_REPLACE_REF_BASE`, `info/grafts` and `shallow` in the common directory (so also for linked worktrees), any `refs/replace/*`, partial-clone configuration, and an unreadable `.git/info` (the permission counterexample Altair fixed in final3). E4 confirmed that `refs/replace` and `info/grafts` each disable the index; shallow repositories are already rejected earlier by `git_version`. I found no case where the index is wrong without being disabled.

### 3. Resource and side-effect safety

- **Pipes and processes.** The merge chunks use `subprocess.run(input=…, capture_output=True)` (communicate: no pipe deadlock, child killed on exception). The graph capture reads stdout and stderr through one selector and stops at the first byte of stderr, the byte cap or the deadline. No temporary files are created by crosswire.
- **Read-only repositories and permissions.** `merge-tree --write-tree` needs to write objects exactly as the scalar call does; when it cannot, the chunk fails and the scalar replay reproduces the original error (E4). `GIT_OPTIONAL_LOCKS=0` is kept. Metadata probes catch `OSError`.
- **L1 object-store side effect (moderate).** A chunk writes the merge trees and conflicted blobs of all its pairs at once. On a complete run the object set after the last pair is the same, but if the run stops early (an operational error at pair *k*) the batch has already written the objects of up to 255 further pairs. In my probe (6 tips, 15 pairs, stop after 3 pairs): the scalar run wrote 6 new loose objects, the batch run 30 (the objects of all 15 pairs). They are unreachable and prunable, nothing observable in the output, and the existing serial code already writes objects; but "the repository is unchanged except for unreachable objects" now includes up to 255 pairs' worth on failing runs. State this in the design note, or bound the chunk for tiny first-pair failures (e.g. first chunk of 16 pairs).
- **L2 unbounded chunk output (moderate).** Unlike the ancestry capture, a merge chunk has no time limit and no output cap. The result of 256 pairs is held in memory as a list of conflicted paths per pair; a repository where many branches conflict on tens of thousands of files (mass reformat or rename) would hold `256 × paths` strings (several hundred MB to GB) where the serial code held one pair at a time. Add a byte cap on stdout (kill, discard, fall back to scalar, as `_parent_graph` does) and treat an over-cap chunk as `None`; also consider sizing a chunk by the previous chunk's output.
- **L3 wasted attempt on large repositories (moderate).** `rev-list --topo-order` must walk the whole history before printing anything, so for repositories above the 20,000-commit bound with ≥4 branches every run pays up to the 1 s capture deadline and then falls back. That is a bounded but permanent constant overhead on exactly the repositories where the scalar path is slowest. A cheap pre-check (`git rev-list --count --max-count=20001` on the same tips is also a full walk, so not free), or the commit-graph file's commit count when present, would avoid it; at least document it and make sure the T22 measurements include one repository above the bound.

### 4. Git 2.38 fallback

The probe sends two self-merges through `merge-tree --stdin --write-tree …`; an unknown option makes `_merge_records` return `None` (non-zero exit, stderr) and disables batching. I confirmed with a wrapper that rejects `--stdin` and reports `2.38.0`: batching disabled, all results identical (E4). The ancestry index needs only `rev-list --topo-order --parents --max-count`, available in 2.38. Altair's notes say a real Git 2.38.0 was built and 315 raw CLI records per side were identical before final3, with a final3 replay still running; I did not repeat it. `int.bit_count` needs Python ≥ 3.10; `requires-python` is `>=3.11`.

### 5. Test gaps

See M1/M2, and:

- **M1 (condition).** The only T22 tests in the tree (`tests/test_t22_parity.py`) were written to pass against the serial source and test the *contract*; the candidate adds **no test that exercises the new code**: nothing for `_PairMerges` (chunk of 256, chunk failure and lazy serial replay, `pair != (a, b)` disabling, probe failure, config guard for driver/filter/promisor, `GIT_TRACE`), nothing for `_PairBases` (agreement with `git merge-base --all` on generated DAGs including criss-cross and unrelated roots, each bound, `refs/replace`, `info/grafts`, unreadable `.git/info`, SHA-256), nothing for `_parent_graph` (stderr, timeout, byte cap, process cleanup). My scratch experiments are the shape of these tests; they are small and deterministic when seeded (the random-DAG generator runs in seconds for 20 repositories). Add them before the commit, using a fake `git` wrapper (PATH shim) for the 2.38 and stderr cases.
- **M2 (condition).** The probe's two self-merges only produce clean records (`status 1`, identical trees). It does not prove that this Git prints *conflict* records and *failure* lines in the format the parser assumes (status 0 plus NUL-terminated paths, an extra empty field per record). The parser is strict enough that an unexpected format degrades to "not trusted", but a different version that prints a *different valid-looking* conflict layout could be parsed wrongly. I verified the format on Apple Git 2.50.1 only. Cheap hardening: make the probe use a scratch repository in a temporary directory (so the user's repository is not touched) with one conflicting pair, and require batch output to equal scalar output for it; or gate batching on a minimum Git version confirmed by CI on at least two versions.
- No test for the object-store side effect (L1) or the memory bound (L2).

## Minor

- **m1** After a failed chunk, the next chunk is attempted again; a repository where every chunk fails pays the speculative cost for each 256 pairs. Disable batching after the first failed chunk.
- **m2** `engine.analyze` reaches into `git._PairBases` / `git._PairMerges` (private names); expose small public factories.
- **m3** The `version` argument of `_PairMerges` is only used as a cache key; either use it (minimum Git version gate) or drop it.
- **m4** `_PairBases._ordinary_history` reads `refs/replace` and configuration on every run of ≥4 branches: three extra Git subprocesses plus the capture even when the repository has few commits; fine, but count them in the "no regression for 4–5 branches" measurements.
- **m5** The docstring of `_PairMerges` says only the original serial call may raise; also state that speculative work can write unreachable objects (L1).
